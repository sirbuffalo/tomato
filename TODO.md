- Decide whether huge-exponent math and the `f` format should refuse a result beyond some size
  Decide whether `exp`, `expm1`, `sinh`, `cosh`, `**`, `int(x)` and the `f` format should refuse a result whose exponent is beyond some size, with a clear error. Today they take time or memory that grows with the exponent: `exp(1e100000)` takes about 16 s, and `f'{1e10000000:.2f}'` writes ten million digits. JSON can now bring such a value in from a 12-byte document. This is a language decision, since the design says the only limit is memory.
- Make `str(int)` subquadratic for big integers
  `tomato_int_str` divides the whole number by 10^9 once per 9 digits. 2^20 bits (315,653 digits) takes 1.75 s, 2^22 28 s, 2^24 over 120 s (estimated 450 s), 2^28 over 90 s (estimated 30 hours); Python 3.14 takes 0.07 s, 0.28 s, 1.4 s and 32 s. A divide-and-conquer conversion (split by 10^(2^k)) needs fast multiply and divide first. Decimal parsing (`int('9' * n)`, big literals) is quadratic too, by the same note in `docs/architecture-review.md`; it was not timed here.
- Add an NTT (three-prime, 64-bit) product above about 10^5 limbs, so 2^28-bit products take seconds
  Big-integer multiplication is Karatsuba (`kara_mul`/`kara_sqr` in `runtime/tomato_rt.c`, n^1.585): a dense 2^24-bit square takes 2.4 s, so a dense 2^28-bit square is still about 3 minutes (81 times that).
