# Releasing

## Release checklist

Work down this list for every release. Steps 4 to 7 happen on the release Mac; `release/release.sh` does all the work of steps 5 and 6.

1. **Before you start (any machine).** `main` is green on GitHub (the macOS Tests and the Linux workflows); `sh site/check.sh` passes; `VERSION`, `std/sys.tom` and `site/wasm/std/sys.tom` name the *previous* version, and `site/latest.json` and `site/config.js` the previous stable one (the `bump` step changes them, and the tests compare `VERSION` with the manifest before it). After any change to `runtime/` or `compiler/`, the committed `site/wasm/*.wasm` were rebuilt (`WASI_SDK=... sh site/wasm/build.sh`; a Linux build is byte-identical to the Mac's) and `compiler/bootstrap/tomatoc.ll` is current (`sh compiler/bootstrap/refresh.sh` says "up to date").
2. **Release notes.** The draft section of [`docs/changelog.md`](changelog.md) describes what changed since the last tag (`git log --oneline vLAST..main`); change its heading to the version and date, and commit and push it to `main` before the run (the script works in its own clone of `origin/main`, so only pushed changes are released). The GitHub release itself gets the generated list of commits (`--generate-notes`); paste the changelog section into it afterwards (`gh release edit vX --notes-file ...`).
3. **Choose the kind of version from the changelog ([Version numbers](#version-numbers)).** Read every entry since the last release and ask of each: can a program that worked before now fail to compile, print something else or stop? Any such change goes under a **Breaking changes** heading in that section. A section with breaking changes needs a new minor (or major) version, `--bump minor`; a patch release (`--bump patch`, 1.0.x) must have none, so if the draft has a Breaking changes heading, a patch release is wrong. This review is the gate: no script can see what a change breaks.
4. **The release Mac is ready.** One-time setup below done; after a restart, log in at the iMac once so the login keychain is unlocked; nothing else running (load at most 2).
5. **Dry run first:** `release/release.sh --dry-run --version 1.0.0` (or `--bump major|minor|patch`, or a pre-release such as `--version 1.1.0-rc.1`) on the release Mac. It runs every step except tagging, publishing and pushing, including the Linux step on biggie over ssh, the copy-back of the Linux results, the publish gate and the snapshot. It has not been run end to end from the Mac yet (`TODO.md`), so the first one is the real check of those parts.
6. **The real run:** `release/release.sh` with the same version flag as the dry run (for 1.0.0: `release/release.sh --version 1.0.0`). On a failure, fix the cause and continue with the command it prints (`--resume`).
7. **Check the result:** the summary's notarization status and sha256 sums; the GitHub release has the `.tar.gz`, `.pkg`, `.dmg` and `latest.json` (and is marked a pre-release for a pre-release); the website shows the new version within minutes (the Pages workflow; a pre-release changes only `latest-pre.json`); `tomato update` on an older install moves to a new patch release, and says to use `--minor` for a new minor version.
8. **Afterwards:** remove release items that the run settled from `TODO.md`.

## Version numbers

From 1.0.0 on, a version is MAJOR.MINOR.PATCH (`1.0.0`, `1.2.10`), optionally followed by a SemVer pre-release: a hyphen and dot-separated identifiers of letters, digits and hyphens, numbers without leading zeros (`1.0.0-rc.1`, `1.1.0-beta.2`). Build metadata (`+...`) is not used. The releases before 1.0.0 were numbered 0.NN (0.1 to 0.51); tools that compare versions read such a number as 0.NN.0. Versions are ordered by [SemVer precedence](https://semver.org/#spec-item-11): 0.51 < 1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta < 1.0.0-rc.2 < 1.0.0-rc.10 < 1.0.0 < 1.0.1 < 1.1.0. The version text is in `VERSION`, `std/sys.tom` (`sys.version()`), the tag `vX` and the file names `tomato-X.tar.gz`, `.pkg` and `.dmg`.

**Compatibility.** All 1.0.x releases are compatible with each other: a program in the implemented subset (`docs/specification.md`) that works on one 1.0.x release works the same on every other one, except for the placeholders in `docs/provisional.md`. A minor release (1.1.0 and later) may change behaviour; each change is listed under Breaking changes in its changelog section and release notes. `tomato update` follows this: it installs a newer patch release at once, and a newer minor or major version only with `tomato update --minor` (it says so and stops otherwise).

**Pre-releases.** A pre-release is published as a GitHub pre-release (never GitHub's "latest") and in `site/latest-pre.json`; `site/latest.json` and the version the website shows (`site/config.js`) keep naming the latest stable release. `tomato update` on a stable install reads only `latest.json`, so it never moves to a pre-release unless asked with `tomato update --pre`; an install that runs a pre-release reads both manifests and moves to a later pre-release or to the release, whichever is higher.

**Choosing the next version.** `release/release.sh` picks it in its `version` step: `--version X` names it (a release or a pre-release); otherwise `--bump major` (1.4.2 to 2.0.0), `--bump minor` (1.4.2 to 1.5.0) or `--bump patch` (1.4.2 to 1.4.3, also what no flag does) counts up from `VERSION`. From 0.51, `--bump major` and `--version 1.0.0` both give 1.0.0; with neither flag the step refuses while `VERSION` is still a two-part 0.NN number, so the first three-part version is always named. After a pre-release, `--version` must name the next one (the release, `--version 1.0.0`, or the next pre-release, `--version 1.0.0-rc.2`). The version must be newer than `VERSION` by precedence and have no tag or GitHub release yet; `release/release.sh --next-version CUR [--version X | --bump P]` prints what a run would pick (the tests use it). A resumed run keeps the version of the run it continues. An installed 0.51 updates to 1.0.0 with the `tomato update` it already has, which compares the numbers part by part. Not tried yet on the Mac: `pkgbuild --version` and the installer with a pre-release text such as `1.0.0-rc.1`; the first pre-release dry run checks it.

## One command: `release/release.sh`

Run it **on the Mac that holds the signing identities** (Davis's iMac). The iMac runs its own byre server, `https://byre-imac-1.tailcecab.ts.net`, with the tomato project shared there. An agent on another server runs the release in a terminal of that shared project (`start_terminal` and `terminal_type` with `server` and that project's `owner_id`), so no ssh is needed and the run survives the agent's turn. Davis's checkout there is in iCloud; the script never changes it, because it works in its own clone:

```sh
release/release.sh --dry-run        # everything except publishing: no tag, no GitHub release, no push
release/release.sh                  # the real release
```

It works in its own private clone (`~/.tomato-release/tomato`, never your own checkout; state and logs are next to it), so "clean, on main, equal to origin" is always true when it starts. It runs these steps in order, prints each one and stops at the first failure:

| step | what it does |
| --- | --- |
| `preflight` | tools (git, clang, Xcode signing tools, gh, and Go, Rust and python3 unless `--skip-bench`), both Developer ID identities **and a real test signature with each** (this catches a locked keychain), the `tomato-notary` profile (`notarytool history`), a WASI SDK, `gh auth` plus write permission on the repository, push access, then the clone is synced to `origin/main`, and the machine must be quiet (1- and 5-minute load average at most `--max-load`, default 2.0; it waits up to `--wait-quiet` seconds, default 900, then refuses). **All** missing things are listed together, each with its fix. |
| `version` | the next version, MAJOR.MINOR.PATCH or a pre-release ([Version numbers](#version-numbers)): `--version X`, or `--bump major`, `minor` or `patch` (the default) from `VERSION`; a `VERSION` that was bumped ahead of its release is used as it is when neither is given. Refuses a version that is malformed, is not newer than `VERSION` by SemVer precedence, or already has a tag or a GitHub release |
| `test` | `tests/run.sh` with the WASI SDK, so the wasm files are rebuilt and compared byte for byte. This runs **before** the version bump because the tests check `VERSION` against `site/latest.json` |
| `bump` | `VERSION`, `site/config.js` (not for a pre-release), `std/sys.tom` (the text `sys.version()` returns) and its browser copy `site/wasm/std/sys.tom` |
| `linux` | the same `tests/run.sh` and benchmarks on a Linux x86-64 machine (`--linux-host`, default `biggie.davismcd.com`) over ssh, on the commit being released (the tests see it before the bump, as the Mac tests do; the benchmarks run with the new version), plus callgrind instruction counts (`benchmarks/count.sh --guest`). The wasm files are not rebuilt there unless `WASI_SDK` is set on that machine; when they are, the comparison is the same as on the Mac, because the build is byte-identical on both (see [The wasm files](#the-wasm-files)). Results come back to `benchmarks/results/linux-x86_64/`. It waits up to `--linux-wait` seconds (300) for that machine's load to drop to `--linux-max-load` (32), then goes on with a warning. **A Linux test failure stops the release** (continue with `--resume --ignore-linux-failures`); an unreachable host, missing tools or failed Linux benchmarks only warn and are recorded in the summary. `--no-linux` skips it |
| `bench` | `benchmarks/run.sh` (10 runs per program in a seeded shuffled order: Tomato, Go, Rust, Python and any other of its languages whose tools are installed; `--runs`, `--seed`), `benchmarks/count.sh` (deterministic instruction counts) when the Lima VM `tomato-count` exists (otherwise skipped with a note) |
| `snapshot` | `release/perf-snapshot.sh`: the `docs/performance.md` section, with Mac and Linux x86-64 columns side by side |
| `build` | `release/build.sh`, `release/pkg.sh` |
| `sign` | `release/sign-pkg.sh` (every Mach-O signed with the Application identity, hardened runtime and secure timestamp; package signed with the Installer identity; notarized with `tomato-notary`; stapled), then independent checks: `pkgutil --check-signature`, `stapler validate`, `spctl`, every Mach-O's signature, the package's scripts, symlink, `Distribution` version, and that the packaged `tomato version` runs; `pkg_sha256` in `latest.json` must equal the signed file's hash. Then `release/dmg.sh` puts that finished package into `tomato-X.dmg` and signs (Application identity), notarizes and staples the disk image; `dmg_sha256` in `latest.json` must equal its hash |
| `commit` | `site/build.sh` (so `site/latest.json`, or `site/latest-pre.json` for a pre-release, has the new version, `pkg_sha256` and `dmg_sha256`), consistency checks, and **one local commit** (`VERSION`, `std/sys.tom`, `site/`, `benchmarks/results/`, `docs/performance.md`; anything else changed stops the run) |
| `publish` | pushes the tag `vX` (the release commit), first requires a recorded passing Linux test run (or `--ignore-linux-failures`) and the signed disk image, then creates the GitHub release (marked a pre-release for a pre-release version) with the package, disk image, tarball and `latest.json`, **downloads them again** and compares sha256 (the public `pkg_url` and `dmg_url` too) |
| `push` | pushes the release commit to main. The site changes only now, after the assets are live and verified. `--no-push` leaves the commit in the clone and says so |
| `summary` | version, tests, benchmark ratios, notarization result, sha256 sums, release URL |

Options: `--dry-run`, `--skip-bench`, `--no-push`, `--version X`, `--bump major|minor|patch`, `--next-version CUR`, `--seed N`, `--runs N`, `--max-load N`, `--wait-quiet SEC`, `--no-load-check`, `--no-linux`, `--linux-host H`, `--linux-tools DIR`, `--linux-max-load N`, `--linux-wait SEC`, `--ignore-linux-failures`, `--branch NAME`, `--origin URL`, `--work-dir DIR`, `--wasi-sdk DIR`, `--host USER@HOST` (optional: stream the script over ssh to another Mac and run it there; needs Remote Login and a key), `--unlock-keychain` (with `--host`: asks for that Mac's login password on your terminal), `--list-steps`, `--help`. Defaults can go in `release/release.conf` (git-ignored; see `release.conf.example`). `--dry-run` also accepts `--skip-notarize` (sign but do not notarize) and `--no-sign`, for a Mac that cannot sign or notarize yet; both are refused without `--dry-run` because an unsigned or un-notarized package must never be published.

**The Linux gate (read this before a real release):** a Linux test failure stops the run at `linux`, and `publish` refuses a real release unless a passing Linux run is recorded, so an unreachable host, missing tools or `--no-linux` also stop it there. Only `--ignore-linux-failures` overrides this, and it needs explicit approval. The 10 Linux x86-64 failures found before v0.51 (LeakSanitizer leaks in five asan tests, progress-bar output, `angles` libm rounding, one REPL message) are fixed. A skipped, unreachable or failed Linux benchmark step keeps the previously committed `benchmarks/results/linux-x86_64` untouched; only a successful run replaces it. The `linux` step comes before the long Mac benchmarks so this fails fast. If pushing main is rejected after publishing, merge (`git pull --no-rebase`), never rebase: the published tag must stay an ancestor of main.

**Failure and resume.** The script ends with the exact command to continue. `--resume` continues at the first unfinished step, `--from STEP` at a named one (steps before it are skipped in this run, but not recorded as done, so a later `--resume` after another failure can go back to an earlier unfinished step), `--restart` throws the unfinished run and the clone's local changes away. A resumed run first re-checks the environment and that the clone still holds only release changes. If `publish` fails halfway, nothing has reached the site (main is pushed last); `gh release delete vX --cleanup-tag -y` undoes a half-made release.

**Deviations from the old manual order, on purpose.** The release commit is made locally before the tag so the tag points at the commit with the new version, but main is pushed only after the published assets are downloaded and verified.

## The steps by hand

The script does exactly this; the rest of this page describes the pieces.


1. `release/build.sh` builds `release/out/tomato-VERSION.tar.gz` and `latest.json`; `release/pkg.sh` (a Mac) adds the unsigned `tomato-VERSION.pkg` and its `pkg_*` fields.
2. Sign and notarize the package (below), then use the signed, stapled package as the release asset. `pkg_sha256` in `latest.json` must be the hash of that final file. Then `release/dmg.sh` wraps that package in `tomato-VERSION.dmg` and signs, notarizes and staples it ([The disk image](#the-disk-image)); with `TOMATO_LATEST_JSON` it adds `dmg_url` and `dmg_sha256`.
3. Publish: `gh release create vVERSION release/out/tomato-VERSION.tar.gz release/out/tomato-VERSION.pkg release/out/tomato-VERSION.dmg release/out/latest.json`, then commit `site/latest.json`. For an existing release, `gh release upload vVERSION FILE --clobber` and update `site/latest.json`; check that the downloaded asset's `shasum -a 256` equals the `pkg_sha256` there.

## The wasm files

`site/wasm/tomatoc.wasm` and `runtime.wasm` are committed, and the `test` step rebuilds them with `site/wasm/build.sh` and requires the same bytes ("wasm files rebuild identically"). Since v0.51 the build gives the same bytes on every host, so wasm built on Linux (`wasi-sdk-24.0-x86_64-linux`) passes this check on the Mac (`wasi-sdk-24.0-arm64-macos`) and the other way round. What makes that hold, and what `build.sh` enforces:

- **WASI SDK 24 exactly.** `build.sh` refuses any other SDK: it checks the clang version line and the sha256 of the sysroot's `libc.a` (that file, `crt1-command.o` and `crt1-reactor.o` are the same in every host's SDK; another SDK version gives other code and another `producers` section).
- **No debug sections** (`-Wl,--strip-debug`). Each host's SDK builds its own compiler-rt (`libclang_rt.builtins-wasm32.a`), whose debug info names that host's build folder (`/Users/runner/work/wasi-sdk/...` on macOS, `/src/src/...` on Linux). Without stripping, a Linux and a Mac build differed only in `.debug_info`, `.debug_str` and `.debug_line`; every other section (code, data, names, producers) was the same. The browser never used the debug sections; stripping also halves `runtime.wasm`.
- **No path of ours reaches the output.** No `-g`, and the runtime does not use `__FILE__` or `assert`, so neither the checkout folder nor the temporary folder matters. wasm-ld writes no timestamps.
- **No host-dependent compiler-rt code.** A few compiler-rt functions differ between the hosts' SDKs in code or data, not only in debug info: the trapping arithmetic helpers (`__addvsi3`, `__mulvti3`, `__absvdi2`, ... which embed their source path through `__FILE__`, so `-ftrapv` would pull them in), `__clear_cache` and `__multc3` (complex `long double` multiplication). `build.sh` stops with their names if one is linked in, and also if any `llvm-project/` path is left in the output. Today's sources link none of them (the 128-bit helpers they do link, such as `__multi3`, `__udivti3` and `__muloti4`, are the same on both hosts).

Checked on Linux x86-64: the Linux build equals the macOS-built files of 812244d with their debug sections removed, byte for byte, and two Linux builds from different checkout paths (one with a space), SDK locations, `HOME`, `TMPDIR`, locale, time zone and umask are identical.

When the check fails, it prints the sections that differ, for each file (`sh site/wasm/sections.sh OLD.wasm NEW.wasm` does the same by hand; with one file it lists the sections with their offsets, sizes and checksums):

- `code`, `data`, `name`, `export` and the like differ: the sources changed and the committed files were not rebuilt, or a change linked something host-dependent that the guard does not know. Rebuild with `site/wasm/build.sh` and commit; if a Linux and a Mac build of the same commit still differ there, rebuild on the Mac and commit that (the Mac is the release host), then add what differs to `build.sh`'s guard.
- `producers` differs: another compiler made one of them (the SDK version check should stop this).
- a `.debug_*` section exists: the files were built by an older `build.sh` without `--strip-debug`. Rebuild and commit.

The suite also checks, without the SDK, that the committed wasm files have no debug sections, so a stale build is caught on every machine.

## Signing and notarizing the package

`release/sign-pkg.sh IN.pkg OUT.pkg` does the whole job and must run on a Mac that holds the signing certificates and the notary login. Both identities, with usable keys, are in the login keychains of Davis's iMac (the release Mac) and MacBook Pro. Do not copy the private keys anywhere else (not to biggie, not into the repository). `release/release.sh` signs on the Mac it runs on; the manual copy-to-a-signing-Mac procedure below is only for a build Mac without the keys.

Environment (defaults shown):

- `TOMATO_PKG_SIGN`: `Developer ID Installer: Davis McDowell (39BK8TGQ26)`, signs the package.
- `TOMATO_APP_SIGN`: `Developer ID Application: Davis McDowell (39BK8TGQ26)`, signs the Mach-O files inside (`tomatoc`) with the hardened runtime and a secure timestamp. Apple rejects the package otherwise (status 4000: "The binary is not signed", "no secure timestamp", "hardened runtime not enabled").
- `TOMATO_NOTARY_PROFILE`: `tomato-notary`, a keychain profile made once with `xcrun notarytool store-credentials tomato-notary` (Apple ID and app-specific password live in the keychain; never write them anywhere).
- `TOMATO_LATEST_JSON`: optional path of a `latest.json` to update with the signed package's hash.

It runs `codesign` on each binary, `productsign`, `pkgutil --check-signature`, `notarytool submit --wait` (on rejection it prints `notarytool log` and fails), `stapler staple`, `stapler validate`, `spctl --assess --type install -vv`, and prints the final SHA-256.

**On the signing Mac itself:** `release/pkg.sh && release/sign-pkg.sh release/out/tomato-VERSION.pkg /tmp/tomato-VERSION.signed.pkg`.

**Agent-driven, from the build Mac (byre client `clitWDw4nYaqr3` is the MacBook Pro):**

1. Build on the server: `release/build.sh && release/pkg.sh`.
2. `copy` `release/out/tomato-VERSION.pkg` and `release/sign-pkg.sh` to `~/Library/Caches/tomato-release/` on the MacBook.
3. `bash` on the MacBook: `cd ~/Library/Caches/tomato-release && sh sign-pkg.sh tomato-VERSION.pkg tomato-VERSION.signed.pkg` (check the exit status, not a piped tail).
4. `copy` the signed file back to `release/out/tomato-VERSION.pkg`, then set `pkg_sha256` in `release/out/latest.json` to `shasum -a 256` of it.
5. Test: `pkgutil --expand-full` the signed file into a temp folder and check that `Scripts/preinstall` and `Scripts/postinstall` in the component are still executable, that `usr/local/bin/tomato` is still a symlink to `../lib/tomato/native/bin/tomato`, that `Distribution` still lists `component.pkg` at the right version, that `lsbom -p MUGsf` on the component `Bom` shows root and wheel for every entry (sign-pkg.sh rebuilds the component with `pkgbuild --ownership recommended` because `pkgutil --flatten-full` records the signer's own owner, and fails if any entry is not root:wheel), and that `tomato version` runs from `usr/local/lib/tomato/native/bin/` there. The expand and rebuild round trip in sign-pkg.sh produced the notarized v0.49 package (Accepted); for extra assurance also install once into a temp volume (`sudo installer -pkg FILE -target /Volumes/TEMP`) if one is available.

Status: done. The Developer ID Application certificate, the Installer certificate and the notary login all exist on the MacBook Pro. The published v0.49 package was re-signed with `sign-pkg.sh` (the `tomatoc` binary signed with the hardened runtime and a secure timestamp), notarized (Accepted), stapled, and passes `stapler validate` and `spctl -a -vv -t install`.

## The disk image

`release/dmg.sh PKG OUT.dmg` runs after `sign-pkg.sh`, on the same Mac. It copies the finished package (signed, notarized and stapled) into a compressed HFS+ image named `Tomato VERSION`, which holds only `tomato-VERSION.pkg`. Then it signs the image with `codesign --timestamp` and the **Application** identity (a disk image is code-signed, not product-signed), notarizes it with `tomato-notary`, staples it, and checks it with `hdiutil verify`, `codesign --verify --strict`, `stapler validate` and `spctl --assess --type open --context context:primary-signature`. Finally it mounts the image read-only and checks that the package inside is byte-identical to PKG, still signed and still stapled. With `TOMATO_LATEST_JSON` it adds `dmg_url` and `dmg_sha256` to that file. `tomato update` ignores both fields, and the download page shows the link. `TOMATO_SKIP_NOTARIZE` and `TOMATO_NO_SIGN` are for dry runs only, as with `sign-pkg.sh`.

## How the website is deployed

Pushing to `main` runs `.github/workflows/pages.yml` (the deploy) and `.github/workflows/tests.yml` (the full `tests/run.sh` on macOS), independently. The deploy runs `site/check.sh` (VERSION, `site/config.js`, `site/latest.json` and its download URLs agree; the pages and wasm files exist), builds `site/`, uploads it and deploys it in a second job (deploy-pages retries once after 30s if its artifact lookup lags behind the upload). It does not wait for the macOS suite, so a failing suite does not keep a release off the website (it still shows red). Deploys queue rather than cancel each other. Nothing is published by hand: the release script's last step pushes main, and the site follows within minutes.
