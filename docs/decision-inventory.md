# Tomato: decision inventory

Every area below still contains **open** decisions. D01, D02, D04, D05, D12, and D15 have partially accepted direction, recorded below. The order organizes discussion; it does not approve any other feature or require its inclusion. “Dependencies” identify questions that inform an area, not a rigid one-way design process.

## Current discussion

1. D01a is accepted: web servers, math, and web apps partly written in Tomato and compiled to WebAssembly. Workload details, ranking, and release scope remain open.
2. D15a and D15b are accepted: LLVM backend and WebAssembly output. Other compilation, platform, and runtime choices remain open.
3. D02a is accepted: simple by default, control when needed. Specific controls remain undecided.
4. D02b is accepted as a goal: faster than Python, with roughly half Go's speed acceptable; avoid major runtime slowdowns for simplicity. Davis confirmed this reading of an ambiguous quote in the byre task. Benchmarks and exact thresholds remain open.
5. D01b is accepted: prime checking and Fibonacci modulo a number are initial math examples. The default integer is settled in D05c; algorithms and modulo rules remain open.
6. D04a is accepted: type checking during compilation is the default. Any explicit dynamic features remain open.
6a. Implementation status (v0.x): the compiler written in Tomato is the only implementation; the Python prototype was retired in v0.6. Everything the prototype had is rebuilt except: constant errors beyond division by zero and fixed-width literals (D05ag, D05ap), `@init` flow analysis (D12x), user-type `&` intersections (D23h), union and `*args` entry inputs (D28b, D39a), spreading at call sites (D39a) and the compile-time cycle notice (D29b); `bundle` is moot (D46a). See "Status of the implementation" in `specification.md`.
7. D04b is accepted: explicit parameter/return types on ordinary named functions, inferred local types where possible. Detailed inference and syntax remain open.
8. D12a and D12b are accepted: include classes and interfaces, with at most one parent class. D12m selects @init as the initialization-function marker. Overriding details, remaining construction/initialization semantics, and dispatch remain open; class assignment is settled in D05a.
9. D12c is accepted: interface conformance requires an explicit declaration checked by the compiler; matching members alone are insufficient.
10. D12d is accepted: a class may explicitly implement multiple interfaces, alongside at most one parent class. Overlapping requirements remain open.
11. D12e is accepted: no default method bodies in interfaces. Other interface member kinds remain open; D12bc settles interface inheritance.
12. D12f is accepted: allow an explicit implementation declaration after a class definition. Exact syntax, duplicate declarations, and processing phase remain open.
13. D12g is accepted: the declaration checks existing methods only; it cannot add methods, and missing required methods fail compilation.
14. D12h is accepted: a module may make the declaration when both the class and interface are imported.
15. D12i is accepted: declarations apply locally and can be shared through explicit export/import. Duplicate handling, import details, re-exports, remain open; D12bb settles passing interface-typed values.
16. D05a is accepted: class assignment copies a reference to the same object, without copying fields. Explicit cloning, field mutability defaults, and value types remain open.
17. D05b is accepted: class arguments share the object through a local parameter; parameter reassignment does not replace the caller's variable. Other parameter modes and non-class arguments remain open.
18. D05c is accepted: ordinary integers are signed, arbitrary-precision, and automatically growing within resource limits. Representation strategy and resource-exhaustion behavior remain open.
19. D05d is accepted: optional fixed-width integer types coexist with the arbitrary-precision default. D05l settles notation and D05y chooses fractional `/`; remaining conversion and division/modulo rules remain open; arithmetic overflow is settled in D05e.
20. D05e is accepted: fixed-width arithmetic reports an overflow error rather than wrapping. D05x settles constant-failure timing; error handling/recovery, remaining conversion rules, and any separate explicit wrapping operations remain open.
21. D05f is accepted: provide signed and unsigned forms of optional fixed-width integers; the ordinary arbitrary-precision integer stays signed. D05g permits programmer-chosen bit lengths; D05l–m settle integer type names. D05n settles unsigned ranges; D05o–r/x settle integer conversion/literal rules and constant-error timing; D05s–w settle addition/subtraction/multiplication typing and D05y–aj settle several fractional division rules. Representation, remaining conversion details, division operand/context rules, integer quotient/modulo, and remaining integer operators remain open.
22. D05g is accepted: fixed-width integer types support arbitrary programmer-chosen bit lengths rather than a preset list. D05h settles selection time; D05i settles the minimum; D05l settles type notation; D05o–r/x settle integer conversion/literal rules and constant-error timing; resource limits, detailed expression grammar, representation and remaining conversions remain open; D05n settles unsigned ranges.
23. D05h is accepted: fixed-width bit lengths must be known at compile time. D05i settles the minimum; D05j permits constant calculations; D05l settles type notation; detailed evaluation rules and resource limits remain open.
24. D05i is accepted: fixed-width bit lengths are positive whole numbers; zero and negative widths are compile errors. D05j permits constant calculations; resource limits and detailed width-expression rules remain open; D05l settles type spelling.
25. D05j is accepted: integer literals, named compile-time integer constants and their arithmetic may supply widths. Results must satisfy D05h–D05i. Exact syntax and evaluation rules remain open.
26. D05k is accepted: signed N-bit integers range from −2^(N−1) through 2^(N−1)−1. Negating the minimum reports overflow; memory encoding remains open; D05n settles unsigned ranges.
27. D05l is accepted syntax: signed `int[length=x]` and unsigned `uint[length=x]`, with a positive compile-time width. D05m names the ordinary type; general generic syntax and detailed expression grammar remain open.
28. D05m is accepted syntax: bare `int` denotes the ordinary signed automatically growing arbitrary-precision integer. `int[length=x]` remains fixed-width; no bare unsigned-growing type is implied.
29. D05n is accepted: `uint[length=N]` ranges from 0 through 2^N − 1 inclusive. Out-of-range arithmetic reports overflow under D05e; encoding and remaining conversions beyond D05o–r/x remain open.
30. D05o is accepted: typed integer assignments, arguments, and returns convert automatically if the destination covers the source type’s entire range. Other changes between distinct integer types require an explicit request; current values do not relax this rule. D05r settles direct literal typing; D05s–w settle integer addition/subtraction/multiplication typing, D05y–aj settle several integer division rules, and D05at settles exact rational addition. Remaining division/context rules, integer quotient/modulo, mixed rational operands, and other operators remain open; D05p settles out-of-range behavior and D05q settles conversion syntax. This narrows earlier references to unresolved conversions.
31. D05p is accepted: ordinary explicit integer conversions report an error for a runtime value outside the destination range, rather than wrap or clamp. D05q settles conversion syntax; D05x settles constant-failure timing; error handling and any separate wrapping/clamping facilities remain open.
32. D05q is accepted syntax: call the destination integer type, as in `int[length=8](value)`, `uint[length=8](value)`, or `int(value)`. This does not settle construction, general calls, type values, or noninteger conversions.
33. D05r is accepted: direct integer literals take an expected integer type when their values fit; out-of-range literals in that position are compile errors. Without an expected integer type they have type `int`. D05v–w settle direct-literal and literal-only addition/subtraction/multiplication contextual typing, with bounded intermediate checks. Constant expressions/contextual typing outside that scope, conversion-operand context, other remaining arithmetic rules, and literal/sign grammar remain open.
34. D05s is accepted: typed integer addition, subtraction, and multiplication use an existing operand type covering both full ranges, also as the result type. If neither range contains the other, require an explicit conversion; do not synthesize a type. Fixed-width overflow checks still apply. D05t settles a literal paired with a typed operand; D05u settles destination context for single operations; D05v settles two direct literals; D05w settles nested addition/subtraction/multiplication typing; D05y–aj settle several integer division rules and D05at settles exact rational addition. Remaining division operand/context/conversion rules, integer quotient/modulo, comparisons, and other operators remain open.
35. D05t is accepted: a direct literal paired with a typed integer in addition/subtraction/multiplication uses that operand’s type if it fits, in either order. Result type is unchanged; an oversized literal is a compile error. D05u makes this independent of destination context for a single operation. D05v settles single operations between two direct literals. D05w settles nested addition/subtraction/multiplication typing.
36. D05u is accepted: a single addition/subtraction/multiplication with a typed operand computes from operand types, then converts the result. A wider assignment, argument, or return type does not widen computation or resolve incompatible operands. D05v settles single operations between two direct literals. D05w settles nested addition/subtraction/multiplication typing.
37. D05v is accepted: one addition/subtraction/multiplication between two direct literals uses the expected integer type for operands and result, otherwise growing `int`. Out-of-range literals are compile errors; fixed-width arithmetic still checks overflow. D05w settles nested arithmetic typing; D05x settles constant-failure timing.
38. D05w is accepted: literal-only addition/subtraction/multiplication subtrees recursively use a typed sibling’s integer type, or the expected type for a wholly literal expression, otherwise growing `int`. Intermediate overflow checks remain. Typed-value subexpressions compute independently from operands. D05y–aj settle several integer division rules, and D05at settles exact rational addition. Contextual typing for other operators, named-constant contextual rules, conversion context, and failure rules outside the accepted constant-error rules remain open.
39. D05x is accepted: constant integer overflow and out-of-range conversions are compilation errors wherever written, even in unreachable ordinary code, for calculations evaluable from literals, compile-time integer constants, and built-in integer arithmetic/conversions. Arbitrary runtime facts need not be proved. Error handling and constant-evaluation resource limits remain open.
40. D05y is accepted: `/` between integer operands means fractional division, with a fraction-capable result type even for whole quotients; `5 / 2` has value 2.5. D05z selects binary64; integer quotient, compatibility, contextual typing, and large-integer details remain open.
41. D05z is accepted: integer `/` produces binary64 floating-point, including whole quotients. Finite precision and range are accepted; D05aj names it `float`, D05ae/ah/ai settle rounding/tiny results/zero signs, and D05af/ag settle overflow response/timing. Other special values, conversions, precise upper boundary, and defaults for other fractional expressions remain open.
42. D05aa is accepted: provide an exact rational type in the standard library alongside binary64 integer division. D05ak names it `rational`. D05al settles growing numeric range. D05aq settles two-integer construction spelling/order. Imports, remaining construction details, storage layout and resources, remaining arithmetic/operators (exact rational + in D05at), remaining normalization details, comparisons, conversions, and errors remain open.
43. D05ab is accepted: integer `/` reports an error for a zero divisor, including `5 / 0` and `0 / 0`, instead of infinity or NaN. D05ac settles constant-case compilation timing; error handling remains open; floating-point-operand and rational-library division are separate.
44. D05ac is accepted: constant integer `/` with a zero divisor fails compilation wherever written, including unreachable ordinary code, for calculations evaluable from integer literals, compile-time integer constants, and built-in integer arithmetic/conversions. Arbitrary runtime facts need not be proved; constant-expression details/resources and error handling remain open.
45. D05ad is accepted: integer `/` rounds the exact mathematical quotient once to binary64, without first approximating operands. Huge identical nonzero integer operands yield 1 subject to resources, even beyond binary64’s finite operand range. D05ae settles ordinary finite-result rounding and D05ah settles tiny results; the precise upper rounding boundary, resource exhaustion, compatibility/contextual typing, and conversions remain open.
46. D05ae is accepted: ordinary finite integer `/` results round to nearest binary64, with exact midpoint ties selecting the even significand (final stored bit zero). D05af selects overflow errors; the precise upper rounding boundary and other operations remain open; D05ah settles tiny results and D05ai settles zero-result signs.
47. D05af is accepted: integer `/` reports an overflow error instead of signed infinity when its binary64 result overflows. This checks the quotient, not operand size. D05ag settles constant-case timing; precise upper boundary, error handling, and other operations remain open; D05ah settles tiny results and D05ai settles zero-result signs.
48. D05ag is accepted: constant integer `/` binary64-result overflow fails compilation wherever written, including unreachable ordinary code, when evaluable from integer literals, compile-time integer constants, and built-in integer arithmetic/conversions. Arbitrary runtime facts need not be proved; precise boundary, constant-evaluation rules/resources, and error handling remain open.
49. D05ah is accepted: extend nearest/ties-even rounding through binary64 subnormals to zero for integer `/`, with no underflow error. Sufficiently tiny nonzero quotients may round to zero. D05ai settles zero-result signs; other operations, resource exhaustion, and general constant evaluation remain open.
50. D05ai is accepted: integer `/` preserves the division sign for binary64 zero results. Tiny negative quotients yield negative zero; integer zero is treated as positive for determining the sign, so `0 / -5` yields negative zero and `0 / 5` positive zero. Printing, comparisons, other operations, and sign inspection remain open.
51. D05aj is accepted: exact lowercase `float` names the fixed-precision binary64 type produced by integer `/`, chosen over `float64`. Other floating types, literal defaults/grammar, and conversions/calls remain open; D05ak names the rational type.
52. D05ak is accepted: exact lowercase `rational` names the standard-library exact rational-number type, chosen over `fraction`. D05al settles growing numeric range. D05aq settles two-integer construction spelling/order. Imports/availability, remaining construction details, storage layout and resources, remaining operators beyond exact rational + in D05at, remaining normalization details, comparisons, conversions, and errors remain open.
53. D05al is accepted: rational numerator/denominator sizes grow automatically without a fixed bit-width ceiling, subject to resources, like `int`. D05am selects automatic lowest-term reduction. Physical layout, remaining normalization details, intermediate arithmetic, resource-exhaustion behavior, remaining construction details (spelling/order in D05aq), and optional alternatives remain open.
54. D05am is accepted: `rational` automatically reduces fractions to lowest terms without manual simplification, including values produced by construction or supported arithmetic. D05an settles positive denominators and canonical zero. D05ao selects an error for zero-denominator construction. Physical storage/internal reduction strategy and APIs remain open.
55. D05an is accepted: reduced rational denominators are positive, signs belong in numerators, and zero has fraction form 0 over 1. This gives one reduced mathematical form per value; physical storage, printed syntax, remaining construction details (spelling/order in D05aq), and APIs remain open; D05ao selects an error for zero-denominator construction.
56. D05ao is accepted: creating `rational` with denominator zero reports an error for either zero or nonzero numerator, rather than infinity or NaN. D05ap settles constant-case compilation timing. D05aq settles two-integer construction spelling/order. Remaining construction details, error handling, and remaining arithmetic operators beyond exact rational + in D05at remain open.
57. D05ap is accepted: rational construction with a denominator evaluable as zero from integer literals, named compile-time integer constants, and built-in integer arithmetic/conversions fails compilation wherever written, including unreachable ordinary code. Arbitrary runtime facts need not be proved. D05aq settles two-integer construction spelling/order. Remaining construction details, error handling, detailed constant-evaluation rules/resources, and remaining rational arithmetic operators beyond exact + in D05at remain open.
58. D05aq is accepted: construct from two integers as `rational(numerator, denominator)`, numerator first and denominator second; `rational(3, 4)` creates three quarters. D05am–ap rules apply; D05ar–as settle the integer-only boundary and independent integer input types. Imports/availability, literal context, named arguments, defaults, other forms, general call grammar, and class construction remain open.
59. D05ar is accepted: both arguments to `rational(numerator, denominator)` must be integers; a `float` argument is a compile-time type error even if whole-valued. D05as accepts integer argument types independently. Float conversion facilities, literal context, and other forms remain open.
60. D05as is accepted: each already-typed rational construction input independently accepts growing int, signed fixed-width, or unsigned fixed-width, with no matching-type requirement. Preserve exact values without narrowing or wrapping; D05am–ap rules apply. Literal context, general mixed arithmetic, and other conversion facilities remain open.
61. D05at is accepted: + between two rational operands computes the exact sum and returns rational, subject to resources, with D05am–an normalization and no float rounding. Mixed operands, other operators, resource-exhaustion behavior, and implementation strategy remain open.
62. D12j is accepted direction: support custom-class + using the requested @add spelling, and provide ways to customize other operators. D12k selects @add as a marker above an ordinary method; D12l selects the left instance receiver/right operand argument shape. Remaining signature rules, operand/result types, dispatch, inheritance, other operator list/spellings, errors, and annotation grammar remain open. (Re-confirmed by Davis in the byre task.)
63. D12k is accepted: @add is a marker above an ordinary method with a programmer-chosen name, designating it as the custom-class + implementation. It is not the method name and does not introduce general-purpose decorators. D12l selects the logical receiver/operand shape. Receiver spelling, operand/result types, dispatch, inheritance, ordinary calls, surrounding grammar, and other operator markers remain open.
64. D12l is accepted: a + b invokes the @add-marked instance method on left operand a, passing right operand b as its one other operand argument. Receiver spelling, declaration grammar, operand/result types, lookup/inheritance, mixed-type selection, right-side fallback, mutation, and ordinary calls remain open.
65. D12m is accepted: @init marks the class initialization function. The signature/receiver, instance-versus-factory behavior, allocation, return value, invocation/construction syntax, inheritance, placement/grammar, and errors remain open. D12n later accepts a class-body typed private-field form; D12u later requires every instance field to be declared in the class body; D12v requires every declaration to give its type; no general decorators are implied. (Re-confirmed by Davis in the byre task.)
66. D12n is accepted syntax: class-body `private name: Type`, including `private x: int[length=8]`. D12r excludes direct subclass access; remaining private access scope/initialization, other forms, and class grammar remain open (D12t settles per-instance storage, D12u requires declaring every field; shared-field syntax remains open); this does not require all fields to be private (D12v requires every declaration to give its type) nor creates a separate struct type. (Re-confirmed by Davis in the byre task.)
67. D12o is accepted: const marks a field that cannot be changed after initialization. D12y settles `private const` order and D12z lets `@init` set a const field once; other modifier placement, exact write checking, const fields that also have declared values, default mutability, inheritance, and errors remain open; D12s settles binding-only const, leaving referenced objects changeable; no compile-time evaluation is implied. (Re-confirmed by Davis in the byre task.)
68. D12p is accepted: methods use def and may have private. D12q selects the prefix def private name. Other modifier order/placement, receiver/parameter/return syntax and annotations, bodies/grammar, remaining private-access scope (D12r excludes direct subclass access), dispatch, and inheritance details remain open. (Re-confirmed by Davis in the byre task.)
69. D12q is accepted syntax: a private-method prefix is def private name, placing private after def and before the method name. This retains lowercase def; complete signatures/receiver, parentheses/punctuation, return annotations, other modifiers, bodies/grammar, defaults, and remaining access rules remain open; D12r excludes direct subclass access. (Re-confirmed by Davis in the byre task.)
70. D12r is accepted (open for Davis: whether inherited parent fields count as declared by the parent’s body or must be redeclared in a subclass, and how this rule applies to them): subclass-defined methods cannot directly read/write parent private fields or call parent private methods; use accessible parent methods instead. lookup/overriding, and error details remain open.
71. D12s is accepted: const fixes an object field’s binding after initialization without freezing its object or nested objects. Accessible mutable fields/methods remain usable through it. Modifier order, initialization/write checking, defaults, inheritance, and errors remain open.
72. D12t is accepted: a class-body field is stored separately in each instance. D12u/D12v later require every field declared with its type; initialization/defaults, shared-field syntax, other modifier placement, inheritance, and errors remain open.
73. D12u is accepted (open for Davis: how “every field declared in the class body” interacts with D12b’s inherited fields): every instance field must be declared in the class body; undeclared field access is a compile error and `@init` assignment does not create fields. D12v later requires the type; initialization/defaults, `@init` checks, and other modifier placement remain open.
74. D12v is accepted: every class-body field declaration gives its type; no inference from initial values. Initialization/defaults, `@init` checks, shared-field syntax, and other modifier placement remain open.
75. D12w is accepted: a class-body field declaration may give an initial value; a field without one must be set by `@init` (D12x: compiler-checked). Value syntax, evaluation order, `@init` checks, shared-field syntax, and other modifier placement remain open.
76. D12x is accepted: the compiler checks that `@init` sets every declared field without an initial value; no hidden type defaults. Exact checking rules, value syntax, shared-field syntax, and other modifier placement remain open.
77. D12y is accepted: with both modifiers a field is written `private const x: int[length=8]`; `const private` is not accepted. Required/other modifiers, value syntax, and shared-field syntax remain open.
78. D12z is accepted: `@init` may set a const field once, on every path through `@init`; the field cannot change afterward. Exact once-only checking, const fields with declared values, inheritance, and other writers remain open.
79. D12aa is accepted: a field or method without a visibility modifier is public; `private` hides it; no `public` keyword. and errors remain open.
80. D12ab is accepted: a method may use private members of any instance of the same class, not only the receiver. Subclass and outside-class access unchanged; errors remain open (D12ac, D12ad settle module and protected access).
81. D12ac is accepted: private members are usable only by methods of their own class; no module or friend access. nested/related classes, and errors remain open.
82. D12ad is accepted: there is no `protected` modifier; parents expose public methods instead. Nested/related classes and errors remain open.
83. D12ae is accepted: a new instance is created by calling the class name with arguments, which runs `@init`; no creation keyword. `@init` signature/receiver/return, parent-class calls, argument defaults/overloading, and errors remain open.
84. D12af is accepted: a class without `@init` can be called with no arguments when every field has a declared value; otherwise it is a compile error. Parent-class calls, argument defaults/overloading, `@init` signature, and errors remain open.
85. D12ag is accepted: a subclass `@init` must explicitly call the parent's `@init`, exactly once, compiler-checked; no automatic parent initialization. Errors remain open (D12ao settles the call spelling; D12ap the ordering) (D12ah settles a subclass without `@init`).
86. D12ah is accepted: a subclass of a class with `@init` must write its own `@init`; otherwise calling it is a compile error; no forwarding of the parent's `@init`. Errors remain open (D12ao settles the call spelling; D12ap the ordering).
87. D12ai is accepted: the `@init` method's name is chosen by the programmer, like `@add`; no reserved name. receiver/signature/return, and errors remain open.
88. D12aj is accepted: a class has at most one `@init`; a second is a compile error. Several creation styles need a separate design. Receiver/signature/return, and errors remain open.
89. D12ak is accepted: a method's receiver is an explicit first parameter named `self`; no implicit built-in name. remaining signature and calling syntax remain open.
90. D12al is accepted: `self` is written without a type; its type is the enclosing class (exception to D04b for the receiver only). remaining signature and `self` in inherited methods remain open (D12am settles the call form).
91. D12am is accepted: a method is called as `instance.method(args)` without writing `self`; the instance becomes `self`. parent-class calls, and errors remain open.
92. D12an is accepted: fields are accessed with a dot; inside a method a field of the receiver is always `self.x`, and a bare `x` never means a field. Local shadowing rules and errors remain open.
93. D12ao is accepted: a subclass `@init` calls its parent's `@init` as `ParentClass.name(self, args)`; no `super`. Use of the class-qualified form for other methods and errors remain open (D12ap settles ordering).
94. D12ap is accepted: the call to the parent's `@init` must be the first statement of a subclass `@init`. Argument expressions, statement definition, longer parent chains, and errors remain open.
95. D12aq is accepted: a `def` without `self` in a class body is a class function with no instance, called through the class name (illustrative `Circle.unit()`); no `self` or instance fields. Inheritance of class functions, subclass-name calls, and errors remain open.
96. D12ar is accepted: a subclass method that replaces a parent method must be marked; marked-but-replacing-nothing and unmarked-but-replacing are compile errors. parent calls, and errors remain open.
97. D12as is accepted: the replacing-method marker is the keyword `override` (Davis's own answer, not an `@` marker). Keyword reservation, and errors remain open.
98. D12at is accepted: `override` goes before `def`, with `private` after `def` (illustrative `override def private area(self)`). Reservation, combination with `@add`/`@init`, and errors remain open.
99. D12au is accepted: a replacing method must have the parent method's name and exactly the same parameter and return types; no variance. Parameter names and errors remain open.
100. D12av is accepted: a replacing method calls the parent's version as `ParentClass.name(self, args)`, same as the `@init` call; no `super`, no required position. Longer chains, other class-qualified calls, and errors remain open.
101. D12aw is accepted: only instance methods with `self` can be replaced with `override`; `@init` and class functions cannot. Name resolution of a same-named subclass class function and errors remain open.
102. D12ax is accepted: a dot-form call on an object runs the replacing method of the object's actual class, chosen at run time; class-qualified calls name their class. D12ay allows parent-typed expressions to hold subclass instances. Interface-typed values are settled by D12bb.
103. D12ay is accepted: a subclass instance can be used wherever its parent type is expected (assignment, arguments, returns). The reverse is an error without D12az's explicit conversion. Interface types, containers, and errors remain open.
