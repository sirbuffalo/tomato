# Triage of `docs/provisional.md` for the 1.0 promise

Date: 2026-11-27 (D109a). Written by the agent for Davis's review; nothing here is decided until Davis answers the list below. The task was the one the language design review asks for in 1.1: give each of the 91 rows one of three outcomes, so that the promise can say "all 1.0.x releases are compatible, except the N features on the unstable list".

| Outcome | Rows | What it means |
| --- | --- | --- |
| Promoted to decided | **58** | part of the promise; the last column of `provisional.md` section 2 cites the decision or the test that pins it |
| Kept on the unstable list | **7** | outside the promise (`provisional.md`, section 1; `releasing.md`, Compatibility says "the 7 features") |
| Removed as superseded | **26** | gone from the promise; section 3 says why and where the behaviour is decided now |

Every promoted row was compared with the current compiler: a small program for each non-trivial row, run with the `tomato` built from `main` on 2026-11-27, or a test that already pins the behaviour. Where the old text no longer matched, the row was **not** promoted as written: its text was corrected (promoted rows below), or the row was removed (P15, P16, P18) or put on the list (P44). `main` moved while this was written (`x is T`, D23i; builtin shadowing, D108a; the release-mode error line, D34c); the rows were re-checked against those changes (P31, P44 and P88 changed).

## Judgment calls for Davis, one by one

Each has my recommendation. Answer with the number and "yes", or say what to do instead. A "yes" to all is the outcome as written.

1. **The error promise (proposed).** `docs/releasing.md` now says: an error id never changes its meaning; the class an operation raises does not change within a minor version; message text may be reworded in a patch release but the first line keeps its id; and a decided rule the compiler does not enforce yet is enforced only in a minor release. Because of the third point, "error message wording" (P20) is on the unstable list as U1. *Recommendation: yes.* If you say no to the wording rule, remove U1 and the promise becomes 6 features, with every message word promised for ever (which I would not do: messages are still being improved).
2. **`!name` foreign functions (U3, P33).** Listed, because review 1.6 may restrict them to `std/` or an opt-in, and they make every `tomato_*` runtime function public. *Recommendation: decide before 1.0 (std-only plus an opt-in flag, as the review proposes), then remove U3; until then it stays listed.*
3. **The edges of the type test (U2, P44).** `main` decided `x is T` while this task ran (D23i, your decision of the review's 2.2), so the spelling is promoted. What stays listed are the things D23i itself marks as defaults or follow-ups: the old `x in T` spelling (kept with a `type-test` warning; error or silent is undecided), and the test on a class- or interface-typed variable, which looks at the declared type, not the object (`a: A = B()` makes `a is B` false; `c: A` holding a `C` that implements `I` makes `c is I` false), so `is` cannot downcast. *Recommendation: decide both before 1.0; fixing the second turns a `False` into a `True`, so it must not wait for a patch release; then remove U2 and the promise says 6 features.*
4. **Entry markers other than `@main` (U4, P21).** Listed until review 2.1 is answered (`@entry name`, or keep `@name`). `@main`, one function per marker (E583) and dotted names (D96a) are decided and promoted. *Recommendation: answer 2.1 before 1.0; the cost of the change grows with every program that uses `@greet`.*
5. **The host input protocol (U5, P84).** `TOMATO_INPUT_ASK=1`, exit code 75 and the echo of answers are the implementer's design; the repl and the website depend on them. Listed. *Recommendation: keep listed (it costs one line), and promote it when the repl or an embedder needs it stable.*
6. **`progress_bar`'s drawing (U6, P68) and `random.choice`/`shuffle`/`sample` (U7, P91).** Both are listed: the bar will probably gain speed and time left; the random helpers want to become methods once generic methods exist. *Recommendation: keep both listed; they are the cheapest honest exceptions.*
7. **Marker names (P23, P65).** I promoted the operator and protocol markers (`@sub @mul @div @floordiv @mod @pow @eq @lt @le @gt @ge @bitand @bitor @bitxor @invert @neg @rmul @hash @set`, and `@len @get @slice @contains @reversed @iter` of D48a). D12k decided the mechanism and the review (2.1) keeps it, but the names beyond `@add` were chosen by the implementer. *Recommendation: promote (changing a marker name later breaks every class that uses it).*
8. **The order tasks run in (P85).** D51a-c and D58a-e decided async; the order tasks run in, the frame layout and the end-of-program rule were the implementer's design, and a dozen tests (`tests/programs/async_*.tom`) pin the order. Promoted. *Recommendation: promote; the unbuilt parts (two tasks reading the same statuses, timeouts, `t.cancelled()`) only add.*
9. **Promoted rows that no decision number of yours backs.** They are the behaviour of every release, checked and tested, but nobody decided them: **P7** (a block starts no new scope; only functions do), **P8** (conditions must be `bool`: no truthiness), **P14** (redeclaring a name with the same type in a function is accepted, another type is E292), **P17** (a subclass may not redeclare a field), and the edge choices of the number-theory helpers **P67, P70, P71, P73, P77, P78, P79** (`prev_prime(2)` raises E42, `nth_prime(0)` E43, `totient(0)` is 0, `is_coprime(0, 0)` is False, `lcm(0, x)` is 0, `is_prime` is a probabilistic test from 3.3 * 10^24 up). *Recommendation: promote all of them. P7 and P8 are the two that shape the language; P7 is Python's function scope and P8 the strictness of Go and Rust *(general knowledge)*; changing either later breaks programs.*
10. **Decided rules the compiler does not enforce or build (P15, P16, and the other gaps in the specification's "Not yet" cells).** I removed rows P15 (class conversion `Circle(s)`, D12az and D12bh: the compiler rejects it with E128 or E324) and P16 (`@init` flow analysis, D12x: the compiler accepts a field left unset) instead of promoting text that does not match. Making the compiler enforce a rule it ignores can reject a program that works today, so the fourth bullet of the proposed error promise puts it in a minor release. Adding a feature that is an error today (class conversion) only adds. *Recommendation: yes; follow-up below: record P15 in `tests/known_gaps`.*
11. **Implementation-note rows removed without a replacement (P36, P39, P40, P41, P42, P52, P53).** Two of them describe something a person can see: the debug-mode report of objects never freed at exit (D29c, P39) and `TOMATO_GC_STATS=1` (P42). I treated both as diagnostics outside the promise rather than listing them. *Recommendation: yes. If you want the leak report promised, it needs its own decision.*
12. **Review items that block 1.0 and are not rows of this file.** If any is still open at 1.0, it must be added to the unstable list, because it would otherwise be a promise nobody decided (1.3, 1.4 and 2.2 are decided and built since: D34c, D108a, D23i): `File` safety (5.1, built as a default by D93a), the sleep clock (6.1), D77g's limits (7.1), `bytes` (8.1), reserved std module names (9.1), `tomato run` inputs (11.1), and the std names that would freeze (2.3, 10: `math.pow`, `datetime_*`, `testing._run_all`). *Recommendation: decide them before 1.0 in the review's ranked order; this triage lists none of them as unstable because that would be a guess.*
13. **The Unicode version (review 1.5).** Not written into the promise: the tables follow Unicode 16.0, and a new Unicode version changes `isalpha`, `isdigit`, case mapping and widths. Since a minor release may change behaviour and lists it, that is already allowed. *Recommendation: say nothing more, but name the Unicode version in the changelog of the release that changes it.*

Not a question: **a compiler warning** when a program uses an unstable feature (review 1.1's suggestion) is not built. The warning needs a new lint kind in `compiler/src/lint.tom`, a bootstrap IR refresh and a wasm rebuild, so it is a follow-up rather than something to slip into a docs change.
