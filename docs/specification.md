# Tomato: living specification

Status: the complete current record of confirmed requirements and accepted language decisions, including typing, classes/interfaces, integers, and fractional division. Unresolved details are identified alongside each rule. This is not yet a complete or implementable language specification.

## Status of the implementation (v0.x)

The compiler written in Tomato is the only implementation. The ~670 tests of the retired Python prototype are at the git tag `v0.5` (`git show v0.5:tests/test_more.py`). `tests/known_gaps/` holds a program for each decided rule it does not meet yet; the test suite fails when one starts to work, so this table and those programs stay honest. The Python prototype that held the features marked "not yet" was retired in v0.6 (it is in git history); each "not yet" item is a follow-up to rebuild in the Tomato compiler. Several decisions below describe behavior of that prototype; where a decision says "interpreter" or "Python compiler", read it as historical.

## Confirmed requirements

These requirements come from Davis's initial brief and subsequent answers. Their unresolved details are listed explicitly.

| ID | Requirement | Still to decide |
| --- | --- | --- |
| R01 | Well designed and easy to use | Intended users, everyday tasks, priorities, and how to evaluate ease of use |
| R02 | Statically typed by default; explicit parameter/return types on ordinary named functions, inferred locals where possible | Detailed inference, annotation syntax, conversions, type relationships, and whether explicit dynamic features exist |
| R03 | Garbage collected | Observable memory behavior, collector constraints, resource cleanup, and runtime costs |
| R04 | Python-like syntax | Indentation, declarations, punctuation, expression rules, and where to differ |
| R05 | Compiled | Compilation model, targets, distribution, and runtime requirements |
| R06 | Every language decision must be explicit | Record substantive choices for Davis to decide; no inherited Python or Go semantics |
| R07 | Somewhere between Python and Go | Which qualities to take from each; no compatibility promise is implied |
| R08 | Use LLVM for compilation | Pipeline, LLVM version, optimization policy, ahead-of-time versus JIT, linking, and supported native platforms |
| R09 | Support web servers and math, including prime checking and Fibonacci modulo a number | Server workloads, algorithms, libraries, additional numeric types, remaining details of accepted fixed-width integers (D05d/f–l) and standard-library rational (D05aa/ak), and concrete performance criteria |
| R10 | Support web apps with parts written in Tomato and compiled to WebAssembly | Host integration, division of responsibilities, browser APIs, runtime/GC strategy, and WebAssembly feature baseline |
| R11 | Aim for faster execution than Python, with performance in Go's general range; roughly half Go's speed is acceptable | Representative workloads, comparison implementations, versions, hardware, metrics, and acceptance criteria |
| R12 | Include classes with single inheritance and explicit implementation of multiple interfaces; permit implementation declarations after a class definition | Fields, methods, construction, overriding rules, detailed interface compatibility, external declaration details, dispatch, and visibility |

## Accepted design direction

- **D01a:** Intended uses include web servers, math, and web apps built partly with Tomato compiled to WebAssembly. These uses are not yet ranked or exclusive.
- **D01b:** Initial math examples are simple prime checking and Fibonacci modulo a number. Default integer range is settled in D05c; algorithms and modulo rules remain open, and other math uses are not excluded.
- **D15a:** LLVM is the chosen compilation backend. This does not select an execution model, native operating systems, or runtime design.
- **D15b:** WebAssembly output is required for the web-app use case. The format of host integration and the runtime strategy remain open.
- **D16a:** A program has no top-level code: files hold only declarations (functions, classes, interfaces, implementation declarations). Execution starts at an entry point, a top-level function marked `@name`. The entry point named `@main` is the default when none is chosen. Davis wrote “no top level code only @main as entry points” and then “@x as entry point … but @main is default if not specified”; this reading (any `@name` is an entry point, `@main` the default, chosen by name when running) is the prototype's interpretation. Arguments, a return value or exit status, several functions with one marker, a program with no `@main`, how an entry is chosen outside the prototype, and module-level constants or variables (which are code) remain open.
- **D17a:** A string literal is written between single quotes or between double quotes, as in `'hello'` and `"hello"`; both mean the same. Single quotes are the recommended style. Davis wrote “strings can use ' or " but ' is recommended”; the prototype reads “recommended” as style guidance only, with no warning, formatter or compile difference. What a string is made of, escapes, a literal containing its own quote kind, multi-line literals, and the string type's operations remain open.
- **D17b:** Strings are UTF-8: text is stored as UTF-8 and is always valid Unicode. Davis wrote “strings are utf8” in chat and later chose “Unicode text stored as UTF-8, working in characters (code points)”, which confirms it. Whether length, indexing and slicing count characters (code points) or bytes, what happens to invalid input, escapes, and the string operations remain open.
- **D17c:** String length, indexing and slicing count characters (Unicode code points), not bytes; slices never cut a character in half. An implementation need not walk a whole string to find a position: it may keep a chunked index for long strings (Davis: “it does not need to always walk through a string especially for long strings it will be in chunks”). Davis later chose “Characters (Unicode code points)” by button, which confirms this reading. The exact structure, whether a “character” should mean code point or something larger (such as a grapheme), the indexing and slicing syntax, and the cost guarantees remain open.
- **D18a:** The loop `for name in x:` iterates over `x`, Python style, alongside `while`; `range` is just another class in the standard library, not special syntax. Davis answered “yes for i in x: range is just another class” to a question offering Python-style `for ... in range(n):` plus `while`. How a class becomes iterable (the iteration protocol), the exact `range` forms and behavior, the loop variable's scope and type, `break` and `continue`, and looping over other collections remain open. The prototype supports only a built-in `range(stop)`, `range(start, stop)` and `range(start, stop, step)` of integers.
- **D19a:** A function or method is written `def name(a: T, b: U) -> R:` followed by an indented body, with `private` after `def` for methods (D12q) and `self` first without a type (D12ak–al). A function with no `->` returns nothing. Davis answered “yes” to this form among three. Default argument values, keyword arguments, how “returns nothing” is spelled, parentheses rules, and error wording remain open.
- **D19b:** A class is declared `class Name(Parent) implements A, B:` followed by an indented body. The parent goes in parentheses and is left out (with the parentheses) when there is none; `implements` and a comma list name the interfaces, and may be left out. Davis chose this over listing everything in the parentheses and over `extends`/`implements` keywords. A separate `Class implements Interface` statement is still allowed (D12f). Error wording for duplicate or unknown names, and whether `implements` can name an interface twice, remain open.
- **D20a:** A list is a growable `list[T]`, written with the literal `[a, b, c]`. Items are indexed from 0 as `names[i]`, the list grows with `append`, and `len(names)` counts items. All items have the same type `T`. Lists are objects: assigning a list shares it, like class instances (D05a). Davis chose this over an immutable list and over a fixed-size array. Negative indexes, slicing and printing follow Python (P81, P82), with helpers such as `sorted` and `sum` (P83). The empty list literal's type, removal and insertion methods and equality remain open; generics beyond `list[T]` are a separate question.
- **D20b:** Maps and sets exist alongside lists. Davis wrote “implement list maps sets”. Their syntax, key rules, ordering, and operations remain open; the prototype uses placeholders (P28).
- **D21a:** Data structures such as syntax trees are modeled with classes. Davis wrote “use clases”. Enums, variants and records are not added now.
- **D22a:** Errors exist, handled with `try`, `catch`, `finally` and `else`. Davis wrote “errors need to exist try catch fianally else”. How an error is raised, what an error is, which failures can be caught, and the exact block forms remain open; the prototype uses placeholders (P29).
- **D23a:** A missing value `None` exists. Davis wrote “none exist”. How a type says “this or None”, whether `None` is a type, and its comparisons remain open; the prototype uses placeholders (P30).
- **D24a:** Files can import from other files and export to them, and a standard library exists. Davis wrote “impory export exist a standar libray ezisst”. The syntax, what is exported by default, naming, search paths, and the library's contents remain open; the prototype uses placeholders (P31).
- **D23b:** An optional value is written as the type `T | None`: a value that is either a `T` or `None`. Davis wrote “None should exist opyional stuff is just Type | None”. This settles how a type says “this or None”. Only `T | None` is decided: general unions (other than with `None`), how a program narrows an optional to `T` (checks, patterns), what operators do on optionals, and whether `None | T` is allowed remain open. The prototype lets an optional flow into a place that needs a `T` and raises a catchable error if it is `None` (P30, P43).
- **D19c:** A function parameter can have a default value, written `name: T = value`, so the caller can leave the argument out. Davis wrote “input:Type | None = None”, as an example, and confirmed with “yes” that it means a default argument (this settles default arguments, which D19a left open). Which expressions a default may use, when it is evaluated, keyword arguments, and whether parameters with defaults must come last remain open; the prototype evaluates a default at each call, in the callee's module, and requires defaulted parameters to be last (P43).
- **D23c:** A value is tested for `None` with `is None` and `is not None`, as well as `== None` and `!= None`. Davis wrote “is None work == None works in None works”; the last phrase was a typo for `| None`, which he later explained (D23d). `is` with anything other than `None` and objects remains open.
- **D23d:** The type of `None` is `None`: `None` names both the value and its type, so `X | None` is the union of the type `X` and the type `None`. Davis wrote “X in None None's type is None”, explaining that the type of `None` is `None`. He then clarified that `x in None` is valid syntax too (D23e). Only unions with `None` are decided; a union of two other types, and whether `None` can appear first (`None | X`), remain open.
- **D45a:** The website compiles and runs Tomato in the visitor's browser: the compiler written in Tomato and the C runtime are WebAssembly, and a JavaScript interpreter runs the IR the compiler writes. No server, no Python. Reading to confirm.
- **D44a:** Editor support lives in `editors/vscode/` (a TextMate grammar, snippets and language configuration) and the website highlights code with the same classes. Reading to confirm.
- **D48a:** A method marked `@iter` and written with `yield` makes its class iterable by `for`; a function with `yield` is a generator that a `for` loops over (its body runs inside the loop, lazily, with no list); the markers `@len`, `@get`, `@slice`, `@contains` and `@reversed` give `len()`, `x[i]`, `x[a:b:c]`, `v in x` and `reversed(x)`. `range(...)` is a class written in Tomato (`std/builtin.tom`) that keeps start, stop and step and prints as `range(0, 100, 1)`. `sum`, `min`, `max`, `sorted` and `list()` take anything with `@iter`. See `docs/decisions.md`.
- **D49a:** `Angle` is a base class in the `math` library, with `Degrees`, `Radians`, `Turns` and `Gradians` subclasses made by `deg(x)`, `rad(x)`, `turn(x)`, `grad(x)`. `sin`, `cos`, `tan` take an `Angle` (a bare float is a compile error); `asin`, `acos`, `atan`, `atan2(y, x)` return one; `a.deg()`, `a.rad()`, `a.turn()`, `a.grad()` convert to floats; `+`, `-`, `* number`, `/ number` and comparisons work on angles of any unit; each angle prints in its own unit (`90 deg`).
- **D49b:** `const name = literal` at the top level (`export const` to share) is a module constant, inlined where used. `math` exports `pi`, `tau`, `e`.
- **D49c:** `math` has `sqrt`, `cbrt`, `hypot`, `exp`, `expm1`, `log`, `log2`, `log10`, `log1p` and the hyperbolic functions with inverses, reached through libm in the C runtime (native and WebAssembly). A value with no answer (`sqrt(-1)`, `log(0)`, `asin(2)`, `exp(1000)`) is a `RuntimeError`.
- **D53a:** `f'text {expr} more'` is an f-string: each `{expr}` is replaced by `str(expr)`, `{{` and `}}` give literal braces; format options such as `{x:5}` are not built.
- **D53b:** `a if condition else b` is a conditional expression (loosest precedence, groups to the right, only the chosen side runs); both sides have one type, except that `None` with a class, text or list gives an optional, and a declared union or optional type converts each side.
- **D53c:** `[item for x in items]` and `[item for x in items if condition]` are list comprehensions over anything a `for` loop accepts; the loop variable is a variable of the function, as in `for`; several `for`/`if` clauses and set/dict comprehensions are not built.
- **D56a:** `abs(x)` (int or float), `chr(n)` and `ord(c)`; `dict.get(key, default)`, `keys()`, `values()` and `items()` (a list of two-item tuples whose item type is `str`, or `str | V`); `str.find(sub, start)`, `rfind`, `count`, `isdigit`, `isalpha`, `isspace`, `lstrip` and `rstrip`. All follow Python except where `docs/decisions.md` D56a says so.
- **D57a:** `Iterable[T]`, `Sized` and `Iterable[T] & Sized` are built-in interfaces: lists, tuples, sets, dicts, text, `range` and any class with an `@iter` (or `@len`) method satisfy them without `implements`. A parameter or field of that type can be looped over (`for x in items`) and measured (`len(items)`). `progress_bar` takes `Iterable[T] & Sized` (D60a). See `docs/decisions.md`.
- **D60a:** A class or function can have type parameters, written in brackets after its name: `class Box[T]:`, `class Pair[A, B]:` (up to two), `def first[T](items: list[T]) -> T:`. T is used as a type inside the declaration. A call finds T from its arguments (`Box(3)` is a `Box[int]`; an `Iterable[T]` parameter takes T from the items of a list, tuple, set, dict, text, range or object with `@iter`), or the one type argument is written out: `Stack[str]()`, `first[str](names)`. Types are written `Box[str]`. Each set of types gets its own compiled copy. `progress_bar` and the `itertools` helpers use this to take any item type. Generic interfaces, generic methods and bounds are not built. See `docs/decisions.md`.
- **D47a:** No top-level code in program files; execution starts at `@main` or another entry point. Only the repl accepts bare statements. This replaces the top-level-code rule of D42a and P60. Davis wrote “No top level”, “Only main” and “Except in repl”; reading to confirm that `@main` stays the default entry and other `@name` entry points remain.
- **D42a:** *[status: its top-level-code rule is replaced by D47a; the repl part stands]* A main program may have top-level statements, which are the program; if there is an `@main`, only it runs. The compiler written in Tomato is v0.x and the Python implementation v-1.x (`VERSION`). `tomato repl` is an interactive prompt that keeps variables and definitions and can compile the session. Reading to confirm.
- **D43a:** The website lives in `site/` (GitHub Pages), releases are GitHub releases described by `latest.json`, `tomato update` installs the newest one, and the project is laid out as `compiler/`, `runtime/`, `std/`, `native/`, `site/`, `editors/`, `release/` (the earlier `python/` and `server/` folders were removed in v0.6). Reading to confirm.
- **D40a:** *[status: intended behavior, NOT implemented in v0.x (see tests/known_gaps)]* Type errors and constant failures are found before the program runs, in every function and method, wherever they are written, including code that never executes (D04a, D05x, D05ac, D05ag, D05ap). The prototype's check pass is partial: it rejects only what it can prove and lets the rest through (P54). Reading to confirm.
- **D41a:** *[status: implemented in v0.17-v0.23 except `rational`, which is the library std/rational.tom (P65)]* `float` is a 64-bit IEEE binary64 (D05z, D05aj) with literals `1.5`, `2e3` and `1.5e-3`; a whole number mixed with a float becomes a float; `//` rounds down; `**` on whole numbers gives a whole number (a negative exponent is an error) and on floats gives a float; `float(x)` and `int(x)` convert; float results must be finite and float division by zero is an error (P55–P58). `rational` is unchanged. Reading to confirm.
- **D39a:** *[status: implemented only in the retired Python prototype; not in v0.x (see tests/known_gaps)]* Functions may take `*args: tuple[T]` and `**kwargs: dict[str, V]`, always typed, last, and in that order, and calls may pass `name=value` keyword arguments. Entry points fill them from the command line: extra inputs become the tuple, `name=value` inputs the dict, each value read as the most restrictive type (D28b). Davis wrote “*args and **kwargs should exist and should work with entries but must be typedqithn tuple or froendcit” (reading to confirm; “froendcit” read as `dict`). `tuple[T]` is an immutable sequence (P48). Interpreter only.
- **D28b:** *[status: implemented only in the retired Python prototype; not in v0.x (see tests/known_gaps)]* An entry point parameter may be a union of `int`, `float`, `bool` and `str`; the input text becomes the first member that accepts it, tried in that order (`6` is an `int`, `1.5` a `float`, `true` a `bool`, anything else a `str`). Davis wrote “should use the most restrictive type so int float bool str” and “that is listed” (reading to confirm). Interpreter only.
- **D38a:** *[status: superseded by D46a: Python is retired; the compiler written in Tomato builds itself, and new features go there]* New compiler and tooling code is written in Tomato (and LLVM IR), not Python; the Python implementation only bootstraps it, and each compiler version compiles the next. - **D23h:** *[status: implemented only in the retired Python prototype; not in v0.x (see tests/known_gaps)]* `&` between types is an intersection (`Named & Printable`) and needs at least one interface among its members (“& only works if at least 1 is a inteface for types”); `&`, `|` and `^` between whole numbers are bitwise and, or and xor with Python’s precedence; `xor` is a logical word operator beside `not`, `and` and `or` (true when exactly one `bool` is true, no short-circuit, between `or` and `and`). This is read together with D29b (best-effort compile-time cycle detection): both hold. The weak-reference syntax, what the leak check reports and when, and how it works with the error modes (D34a) remain open. The prototype has neither (it relies on Python's memory management).
- **D37a:** Class instances always use pointers: an instance is a heap object reached through a pointer, never stored inline in another value, so assigning or passing one shares the object. Davis wrote “classes always use pointeres”. This agrees with D05a and with the compiler's layout. Where the IR comes from, pointer and aggregate types, and calling conventions beyond these remain open. This is a delegated decision made by me; Davis can change it.

How async is written (keywords, what it awaits), the threading library's contents, how they interact with reference counting (D29a), and the web-server model remain open.

Davis wrote “int auto fetects some size and edcides”; this is my reading (it could also mean a fixed size chosen by the compiler, which would change D05c). ## Accepted detailed semantics

**D04a — Compile-time type checking:** check ordinary code's type compatibility during compilation. Reject known type mismatches before running, including in ordinary code that would not execute. This does not promise detection of every runtime failure. Detailed inference, conversions, and any explicit dynamic features remain open.

**D04b — Annotation policy:** require explicit parameter and return types on ordinary named functions; infer local variable types when possible. Annotation syntax, precise inference rules, ambiguous cases, lambdas, generics, method/receiver details, and module-level declarations remain separate decisions.

**D12b — Single class inheritance:** a class may inherit fields and methods from at most one parent class and replace selected inherited methods. Multiple class inheritance is excluded. D12m selects @init as the initialization-function marker. Exact overriding, remaining initialization/construction details, visibility, dispatch, and subtype rules remain open. This does not limit or settle interface implementation or interface inheritance.

**D12c — Explicit interface conformance:** interface implementation must be explicitly declared and checked by the compiler. Matching members alone do not establish conformance. D12f permits the declaration after the class definition. Detailed compatibility, inherited conformance, and other interface capabilities remain open.

**D12d — Multiple implemented interfaces:** a class may explicitly implement several interfaces while inheriting from at most one parent class. Overlapping requirements and interface inheritance remain open.

**D12e — No interface default bodies:** interfaces declare method requirements but do not supply default method implementations. This does not settle other interface member kinds or the details of outside-class declarations; D12f–g later settle that separate declarations only check existing methods and cannot add missing ones.

**D12f — Declaration after a class definition:** support a separate statement explicitly declaring that an already-defined class implements an interface. The illustrative form is `Class implements Interface`; exact spelling and grammar remain open. This refines D12c's explicitness requirement rather than introducing automatic conformance. D12i specifies visibility; duplicate declarations and whether such statements can execute at runtime remain undecided.

**D12g — Check existing methods only:** the separate implementation declaration checks that the class already supplies methods compatible with the interface. Missing required methods cause a compilation error. The declaration cannot supply missing methods or add methods to the class. Precise compatibility, inherited member handling, and member visibility details remain open; D12i settles declaration sharing scope.

**D12h — Imported class and interface permitted:** a module may explicitly declare that an imported class implements an imported interface. It need not define either one. The compiler still checks compatibility under D12g. D12i settles sharing: the relationship is local unless exported, and another module uses it through an explicit import. How this interacts with member visibility is undecided; detailed member access and import/export syntax remain open.

**D12i — Share declarations through explicit imports:** a separate implementation declaration applies locally unless exported. Another module may use the exported relationship by explicitly importing the declaration; it does not automatically apply throughout the program. This concerns using a concrete class where an interface is required. Detailed export/import syntax, re-exports, duplicate declarations, remain open; D12bb settles passing interface-typed values.

**D12j — Custom-class operator support using `@add`:** support custom classes using `+`, with the requested spelling `@add` for addition customization. Davis also requested ways for classes to use other operators, without selecting their list or spellings. This provides arithmetic-style syntax for programmer-defined classes at the cost of operator-definition and dispatch rules. D12k selects `@add` as a marker above an ordinary method; D12l selects the left instance receiver/right operand argument shape. Remaining signature rules, operand/result types, dispatch, inheritance, supported other operators, error behavior, and broader annotation grammar remain open. Davis re-confirmed this in the authenticated byre task (2026-11-08).

**D12k — `@add` marks an ordinary method:** place `@add` above an ordinary method with a programmer-chosen name to designate that method as the implementation of `+` for a custom class. It is a marker, not the method’s reserved name. Chosen over a special method named `@add` to permit descriptive method names, at the cost of a separate marker-to-operator relationship. This does not introduce general-purpose decorators. D12l selects the logical receiver and operand shape. Receiver spelling, operand/result types, dispatch, inheritance, ordinary method-call details, precise surrounding grammar, and other operator markers remain open.

**D12l — Left instance receiver for custom `+`:** for `a + b`, invoke the `@add`-marked instance method on the left operand `a`, passing the right operand `b` as its one other operand argument. Chosen over a class-associated method with two explicit operands to attach addition behavior to the left object without passing it twice. This selects the logical receiver/operand shape, not receiver source spelling or declaration grammar. Operand/return types, method lookup and inheritance, mixed-type selection, right-side fallback, mutation, and ordinary method-call details remain open.

**D12m — `@init` marks the initialization function:** identify a class’s initialization function with the marker `@init`. Davis gave this answer when asked whether fields are declared in the class body or inferred from initialization assignments; it chose neither option. D12u later chose declaration in the class body. This gives initialization an explicit role marker; its relationship to allocation, instance versus factory behavior, signature, return value, invocation/construction syntax, inheritance, exact marker placement/grammar, and error handling remain open. D12n later accepts a class-body typed private-field declaration form; D12u later requires every instance field to be declared in the class body; D12v requires every declaration to give its type. This marker does not introduce general-purpose decorators. Davis re-confirmed this in the authenticated byre task (2026-11-08).

**D12n — Typed private-field declaration form:** support class-body field declarations of the form `private name: Type`, including Davis’s exact example `private x: int[length=8]`. The `private` modifier precedes the field name, and a colon separates the name from its explicit type. This accepts a declaration form, not a requirement that every field use this modifier; D12v requires every declaration to give its type. D12r excludes direct subclass access. The remaining private-access boundary, initialization, other declaration forms, and surrounding class grammar remain open. D12t settles per-instance storage and D12u requires every field to be declared; shared-field syntax remains open. No separate struct type is selected. Davis re-confirmed this in the authenticated byre task (2026-11-08).

**D12o — Const fields cannot change after initialization:** provide the field modifier `const`; after initialization, a field marked `const` cannot be changed. This follows Davis’s direct request, reading “after unit” as “after init” in the initialization discussion. Exact modifier placement/order, permitted writes during initialization, how completion and later writes are checked, default mutability, inheritance interactions, and error reporting remain open. D12s settles referenced-object effects: const fixes the field binding without freezing the object. Compile-time constant evaluation is not implied. Davis re-confirmed this in the authenticated byre task (2026-11-08).

**D12p — Methods use `def` and may be private:** define class methods using the keyword `def`; a method may also have the modifier `private`. These are direct requested spellings/capabilities, not a selection of Python method semantics. D12q places `private` after `def` and before the method name. Receiver/parameter/return syntax and annotations, other modifier ordering, method bodies and broader grammar, the remaining private-access boundary (D12r excludes direct subclass access), dispatch, and inheritance interactions remain open. Davis re-confirmed this in the authenticated byre task (2026-11-08).

**D12q — Private-method declaration prefix `def private name`:** place the optional `private` modifier after the method keyword `def` and before the method name, as in `def private x`. This is a declaration prefix, not a complete signature: receiver/parameters, parentheses and punctuation, return annotations, other modifiers, method bodies, and remaining private-access semantics remain open; D12r excludes direct subclass access. It retains D12p’s lowercase `def` keyword. Davis re-confirmed this in the authenticated byre task (2026-11-08).

**D12r — Parent private members are hidden from subclass-defined methods:** a method defined in a subclass cannot directly read or write its parent class’s private fields or call its parent’s private methods. It uses accessible parent methods instead. This chooses no direct subclass access; lookup/overriding, and error details remain open. Open interaction for Davis: how this applies to parent fields inherited under D12b (versus fields redeclared in a subclass) is undecided.

**D12s — Const fields fix the binding, leaving referenced objects changeable:** when a const field holds an object, the field cannot be replaced with a different object after initialization, but accessible mutable fields and methods on the referenced object remain usable through it. For example, a const owner field holding a Person cannot be reassigned, while that Person’s mutable name may still change. These names illustrate the rule, not new syntax. Const does not freeze the object or its nested objects. D12y settles `private const` order and D12z lets `@init` set a const field once; other modifier placement, exact write checking, const fields that also have declared values, default mutability, inheritance, and error details remain open.

**D12t — Class-body fields belong to each instance:** a field declared in a class body, such as the accepted `private x: int[length=8]`, is stored separately in each instance; each instance holds its own `x`, and changing one instance’s `x` does not change another’s. Shared (per-class) fields would need a separate later design. D12u requires every field to be declared and D12v requires its type; initialization and defaults, other modifier placement, and shared-field syntax remain open.

**D12u — Every instance field must be declared in the class body:** an instance field exists only if the class body declares it (the D12n form); reading or writing an undeclared field is a compile error, and assignment in `@init` does not create fields. The class body therefore lists every field and its declaration. Open interaction for Davis: D12b lets a class inherit a parent’s fields, so whether an inherited field counts as declared by the parent’s body (versus being redeclared in the subclass) is not yet decided. The `self.count = 0` example is illustrative, not accepted syntax. Initialization and defaults, `@init` write checks, and other modifier placement remain open.

**D12v — Field declarations always give the type:** every class-body field declaration names its type, as in the accepted `private x: int[length=8]`; a declaration without a type is not allowed, and types are not inferred from initial values. Chosen over inferring the type from an initial value, at the cost of a few characters per field. Initialization values and defaults, `@init` write checks, shared-field syntax, and other modifier placement remain open. This follows D12u.

**D12w — Field declarations may give an initial value:** a class-body field declaration may include an initial value, so each new instance starts with that value for the field unless `@init` changes it. A field declared without a value must be set by `@init`; D12x makes the compiler check this. The example `private x: int[length=8] = 0` is illustrative, not accepted syntax. The value syntax, evaluation time and order, whether the value may be an arbitrary expression, `@init` write checks, shared-field syntax, and other modifier placement remain open.

**D12x — Fields without a value must be set by `@init`:** the compiler checks that `@init` sets every declared field whose declaration gives no initial value; there are no hidden type-default values. The exact checking rules (for example, paths, branches, reads before setting, and error wording) remain open. Value syntax and evaluation order, shared-field syntax, and other modifier placement also remain open.

**D12y — Field modifier order is `private const`:** when a field declaration has both modifiers, `private` comes before `const`, as in `private const x: int[length=8]`; the other order is not accepted. This follows the `def private name` style of D12q. It does not decide whether `private` is required or what the  is, nor whether other modifiers exist. Value syntax and evaluation order, and shared-field syntax remain open.

**D12z — `@init` may set a const field once:** `@init` is the place a `const` field may be assigned, and only once on every path through `@init`; after `@init` completes, the field cannot change (D12o). A const field with no declared value must be set there (D12x). The exact once-only checking rules (branches, loops, reads before setting, error wording), const fields with declared values, inheritance, and other writers remain open.

**D12aa — Members are public unless marked `private`:** a field or method with no visibility modifier is reachable from other code; the modifier `private` hides it (D12n, D12p–q), and no `public` keyword is introduced. Hidden parent members stay inaccessible to subclass methods (D12r). other visibility modifiers, and error details remain open.

**D12ab — Methods may use other instances’ private members of the same class:** inside a class, a method may read or write a `private` field, or call a `private` method, of any instance of that same class, including an instance other than the receiver. This does not extend to subclass methods (D12r) or to code outside the class. access from nested or related classes, and error details remain open.

**D12ac — Private means inside the class only:** a `private` member can be used only by methods of its own class (D12ab). Other functions and classes in the same module, and subclass methods (D12r), cannot use it directly; they use accessible members. No module or friend access exists. Nested or related classes, and error details remain open.

**D12ad — No protected level:** Tomato has no `protected` modifier. A class that wants subclasses to use something makes it public (unmarked, D12aa); `private` members stay inside the class (D12ac). Nested or related classes and error details remain open.

**D12ae — Instances are created by calling the class name:** writing the class name with arguments, such as the illustrative `Point(1, 2)`, allocates a new instance and runs its `@init` with those arguments. There is no separate creation keyword. This follows the type-call style of D05q and D05aq without making conversions and construction one feature. `@init`'s signature, receiver spelling and return value, calls through a parent class, overloading or defaults for arguments, and error details remain open.

**D12af — A class without `@init` can be called when every field has a declared value:** calling such a class, as in the illustrative `Counter()`, creates an instance with the declared values and takes no arguments. A class without `@init` that has any field lacking a declared value is a compile error (D12x). No empty `@init` is needed. Calls through a parent class, argument defaults or overloading, `@init`'s signature, receiver and return value, and error wording remain open.

**D12ag — A subclass `@init` must explicitly call the parent’s `@init`:** when a subclass defines `@init`, the parent’s initialization runs only where the subclass’s `@init` calls it, with the arguments the subclass chooses, and the compiler checks that the call happens exactly once. Nothing runs the parent’s `@init` automatically. The spelling of the parent call, whether it must come first, reads of fields before the parent call, and error wording remain open.

**D12ah — A subclass of a class with `@init` must write its own `@init`:** if a parent class has an `@init`, a subclass without its own `@init` cannot be called; this is a compile error. The subclass’s `@init` calls the parent’s (D12ag). The subclass does not reuse or forward the parent’s `@init`. A subclass of a parent without `@init` follows D12af. Error wording remains open (D12ao settles the call spelling and D12ap that the call comes first).

**D12ai — The `@init` method’s name is chosen by the programmer:** `@init` marks an ordinary method whose name the programmer picks, as `@add` does (D12k); the name is not fixed or reserved. The illustrative `@init` above `def start(self, size: int)` is not accepted syntax. How the subclass’s call to the parent’s `@init` is spelled, the signature, return value, and error wording remain open.

**D12aj — A class has at most one `@init`:** a class may have at most one method marked `@init`, so calling the class name always means that method; a second `@init` in the same class is a compile error. Other ways to offer several creation styles would need a separate design. The `@init` signature, return value, and error wording remain open.

**D12ak — Methods take an explicit first parameter named `self`:** a method names the instance it runs on through an explicit first parameter named `self`, as in the illustrative `def area(self)`. The receiver is not an implicit built-in name. D12aq settles `def` without `self` and D12am the dot call; the rest of the parameter and return syntax remains open.

**D12al — `self` has no written type:** inside a class, `self` is written without a type annotation; its type is the enclosing class. Writing a type for `self` is not part of the language. This is a stated exception to D04b’s explicit parameter types for the receiver only. the other parameters’ and return syntax, and how `self` is typed within an inherited method remain open.

**D12am — Methods are called with a dot on the instance:** a method is called as `instance.method(arguments)`, as in the illustrative `c.area()`; the call does not write `self`, and the instance before the dot becomes `self`. Passing the instance as an ordinary first argument is not the ordinary calling form; D12ao accepts it only for a subclass `@init` calling its parent’s. calls through a parent class, and error wording remain open.

**D12an — Fields are accessed with a dot, and inside methods as `self.x`:** a field is read or written with a dot on an instance, as in the illustrative `c.x` (subject to `private`, D12ac). Inside a method, a field of the receiver is always written `self.x`; a bare `x` never means a field. This follows D12ak–al. Shadowing rules for locals, access to other instances’ fields (D12ab) beyond the dot form, and error wording remain open.

**D12ao — The parent’s `@init` is called by naming the parent class and passing `self`:** a subclass `@init` calls its parent’s `@init` by writing the parent class name, a dot, the parent’s `@init` name, and `self` as the first argument, as in the illustrative `Shape.start(self, name)`. No `super` keyword is introduced. D12aq adds calls to class functions through the class name. Whether the `self`-passing form may call other instance methods beyond D12av’s parent-version call, and what happens when the parent chain is longer, remain open, as do longer parent chains, and error wording.

**D12ap — The parent `@init` call is the first statement:** in a subclass `@init`, the call to the parent’s `@init` (D12ao) must be the first statement, so the parent part is set up before any subclass code runs and subclass code can rely on parent fields. A subclass cannot run earlier statements, for example to compute a parent argument; it can compute that argument inline in the call. Whether the arguments may use other expressions, exact statement and error wording, and what counts as a statement for this rule remain open.

**D12aq — A `def` without `self` is a class function:** a `def` in a class body with no `self` parameter is a function that belongs to the class and has no instance. It is called through the class name, as in the illustrative `Circle.unit()`, and cannot use `self` or instance fields. It may use the class’s private members of instances it is given (D12ab), and may be marked `private` (D12p–q). Whether class functions are inherited or replaced by subclasses, how a call through a subclass name resolves, whether `@init` may be one, and error wording remain open.

**D12ar — A subclass marks a method that replaces a parent method:** a subclass method that replaces an inherited parent method must carry a marker above it, in the style of `@add` and `@init`; a marked method that replaces nothing is a compile error, and an unmarked method that would replace a parent method is a compile error. D12as spells the marker as the keyword `override`. D12au settles the match rule and D12av calls to the replaced parent method; and error wording remain open.

**D12as — The replacing-method marker is the keyword `override`:** the marker required by D12ar is spelled `override` and is a keyword, not an `@` marker; this is Davis’s own answer (“Override keyword”), chosen outside the offered `@override` and `@replace`. D12at places it before `def`; whether the keyword is reserved everywhere, and error wording remain open. This does not change `@add` and `@init`, which remain `@` markers.

**D12at — `override` goes before `def`:** a replacing method is written with `override` before `def`, and `private` stays after `def` (D12q), as in the illustrative `override def private area(self)`. The `override` keyword leads the declaration. Whether `override` is reserved everywhere, whether it may be combined with `@add` or `@init`, and error wording remain open.

**D12au — A replacing method must match the parent’s name and types exactly:** an `override` method matches a parent method only when it has the same name and exactly the same parameter types and return type; otherwise it is a compile error. There are no compatible-signature or variance rules. Whether `self` and parameter names take part in the match, and error wording remain open.

**D12av — A replacing method calls the parent’s version the same way:** inside an `override` method, the parent’s version is called by naming the parent class and passing `self`, as in the illustrative `Shape.area(self)`, the same form as the parent `@init` call (D12ao). No `super` keyword is introduced. Unlike the `@init` call (D12ap), this call has no required position. Longer parent chains, calling a method the parent itself inherited, whether any instance method may be called in this class-qualified form, and error wording remain open.

**D12aw — Only instance methods with `self` can be replaced:** `override` applies only to instance methods that take `self`. `@init` is never replaced (each subclass writes its own, D12ah), and class functions (D12aq) are not replaced. A subclass class function with the same name as a parent’s is a separate function reached through the subclass name; this was part of the chosen option’s description, and how such a call resolves through each class name remains open. Error wording remains open.

**D12ax — The subclass’s replacing method runs, chosen at run time:** when an instance method is called through the dot form (D12am) on an object whose class replaced it with `override`, the replacing method of the object’s actual class runs, chosen when the program runs. The illustrative `s.area()` with `s` declared as `Shape` and holding a `Circle` runs `Circle`’s `area`. D12ay allows a parent-typed expression to hold a subclass instance, which is where this rule matters. Class-qualified calls (D12ao, D12av) name their class and do not use this lookup. and error wording remain open.

**D12ay — A subclass instance can be used wherever its parent type is expected:** a value of a subclass type can be assigned to a variable, passed as an argument, or returned where a parent class type is written, as in the illustrative `s: Shape = Circle(2.0)`. The reverse (a parent-typed value where a subclass type is expected) remains an error without the explicit conversion of D12az. This settles the assumption under D12ax. Assignment through interface types, containers of subclass instances, and error wording remain open.

**D12az — A parent value can be converted to a subclass with a checked type-call:** a parent-typed value can be converted to a subclass type with an explicit type-call, as in the illustrative `Circle(s)` where `s: Shape`; the conversion fails with an error when the object is not a `Circle`. This resembles creating a new instance by calling the class name (D12ae); D12ba settles the overlap by rejecting the ambiguous class. The failure error’s form, conversions to interface types, and conversions between unrelated classes remain open.

**D12ba — The compiler rejects a class whose call is ambiguous:** a class whose `@init` takes a single parameter whose type accepts a value of the class’s own parent type, or of the class’s own type, is a compile error, so a call `Circle(x)` never means both creation (D12ae) and conversion (D12az). Copying an instance needs a differently named method. The exact set of rejected parameter types (for example, parameters of types between the class and its ancestors, or interface types), and error wording, remain open.

**D12bb — An instance can be used where an interface it implements is expected:** an interface can be written as a variable, parameter or return type, and any instance of a class that explicitly implements it (D12c–d, D12f–i) fits that type. A dot-form call on such a value runs the actual class’s method, chosen at run time (D12ax). This matches D12ay for parent classes. Davis answered this after the question had been withdrawn, and chose to stop asking questions. Interface-to-class conversions, interface inheritance, generic or container interface types, and error wording remain open.

**D12bc — An interface can extend one or more interfaces:** an interface may name one or more parent interfaces. A class that implements the child interface must provide the methods of every parent as well, and an instance of it fits the child type and each parent type (D12bb). Overlapping requirements between parents, cycles, and error wording remain open.

**D12bd — One method can satisfy overlapping interface requirements:** when two interfaces, whether implemented by one class (D12d) or extended by one interface (D12bc), require a method with the same name and the same signature, a single method in the class satisfies both. The same name with a different signature is an error. Cycles and error wording remain open.

**D12be — Interface inheritance cannot form a cycle:** an interface may not extend itself, directly or through other interfaces (A extends B and B extends A is an error). Error wording remains open.

**D12bf — Subclasses inherit implemented interfaces:** when a class implements an interface, each of its subclasses also counts as implementing it with no further declaration, and its instances fit that interface type (D12bb). A subclass's replacing methods must still fit the interface. Error wording remains open.

**D12bg — A method fits an interface requirement by exact types:** a class method satisfies an interface method requirement when its parameter types and return type are exactly those of the requirement. Parameter names do not need to match. Accepting broader parameters or returning narrower types does not count. Error wording remains open.

**D05a — Class assignment shares the object:** assigning a class instance copies a reference to the same object; it does not copy the object's fields. Mutations to an allowed mutable field are visible through either reference. Explicit copying, field mutability defaults, and separate value types remain open.

**D05b — Class arguments share objects with local parameters:** by default, passing a class instance copies its reference into a local parameter. Permitted mutations affect the shared object, but assigning a different object to the parameter does not replace the caller's variable. In the counter example, changing its field from 0 to 1 and then rebinding the parameter to a new counter holding 99 leaves the caller's original counter at 1. Explicit alternative modes, non-class arguments, and mutability defaults remain open.

**D05c — Arbitrary-precision default integers:** ordinary whole numbers are signed integers that grow automatically as needed, subject to available resources. They have no fixed bit-width limit and do not silently wrap or truncate to a fixed range. For example, adding one to 9,223,372,036,854,775,807 yields the exact integer 9,223,372,036,854,775,808 if resources permit. D05m names this type `int`. D05d–l require optional signed/unsigned fixed-width integers; D05aj names binary64 `float`, and D05aa/ak require standard-library `rational`. D05o–x settle integer conversion/literal/arithmetic rules, and D05y–aj settle several integer fractional-division rules. Representation strategy, resource-exhaustion behavior, any additional numeric types, remaining conversion details, division operand/context rules, and integer quotient/modulo remain open. The performance goal remains a goal to validate, not a demonstrated property.

**D05d — Optional fixed-width integers:** offer explicitly chosen fixed-width integer types alongside the arbitrary-precision default. D05l settles fixed-width type notation; D05o settles automatic lossless conversions; D05p settles out-of-range explicit conversions; D05q settles integer conversion syntax; D05g permits programmer-chosen bit lengths. Arithmetic overflow reports an error under D05e, and both signed and unsigned forms are required under D05f. Their inclusion does not change ordinary integer semantics or guarantee a particular speedup.

**D05e — Fixed-width arithmetic reports overflow:** when an arithmetic result exceeds the chosen fixed-width integer type's representable range, report an overflow error rather than wrap around. For the signed `int[length=8]` type accepted by D05g/k/l, adding values 127 and 1 reports overflow instead of yielding −128. D05g permits programmer-chosen widths, and D05l settles their type notation. The error representation, handling/recovery mechanism and any explicitly requested wrapping operations remain open; D05x settles constant-failure timing; D05p settles out-of-range explicit conversion behavior. Ordinary arbitrary-precision integers retain D05c's behavior.

**D05f — Signed and unsigned fixed-width integers:** include both signed and unsigned forms of the optional fixed-width integer types. The ordinary automatically growing integer remains signed. D05g permits programmer-chosen bit lengths. D05l settles type notation. D05n settles unsigned ranges. Representation, remaining arithmetic rules beyond D05s–w and D05y–aj, and remaining conversion rules remain open. D05e's overflow-error rule applies to either form.

**D05g — Arbitrary fixed-width bit lengths:** fixed-width integer types support programmer-chosen bit lengths rather than a prescribed list of sizes. For example, 7-bit and 19-bit widths are permitted; D05l supplies accepted forms such as `int[length=7]` and `uint[length=19]`. A fixed-width integer's range remains bounded by its selected width; this is distinct from ordinary automatically growing integers. D05h requires compile-time-known widths. D05i requires a positive whole-number width. D05j allows constant calculations. D05l settles fixed-width notation. Resource limits, detailed constant-evaluation rules, representation and remaining conversion rules remain open; D05n settles unsigned ranges. Both signed and unsigned forms and D05e's overflow-error policy remain required.

**D05h — Width known at compile time:** the bit length of a fixed-width integer type must be known during compilation. A running program cannot directly define such a type using a width read from input. This keeps width in static type information. D05j allows compile-time constant calculations. D05l settles fixed-width notation. Detailed expression/evaluation rules, resource limits, and remaining conversion rules remain open; D05i settles the minimum width. Ordinary automatically growing integers are unaffected.

**D05i — Minimum fixed width of one bit:** a fixed-width integer type's bit length must be a positive whole number. Zero and negative widths are compilation errors; zero-bit integer types are excluded. This applies to signed and unsigned forms. D05j allows constant calculations. Resource limits, detailed width-expression rules, and memory representation remain open; D05n settles unsigned ranges; D05l settles fixed-width type notation.

**D05j — Constant calculations for widths:** a width may be an integer literal, a named compile-time integer constant, or arithmetic using compile-time integer constants. For illustration, a compile-time constant of 10 multiplied by 8 can supply an 80-bit width; D05l supplies the type notation. The result must be known during compilation and satisfy D05i's positive whole-number requirement. Detailed expression/evaluation rules, constant declaration syntax, resource limits, and any broader compile-time execution capabilities remain open.

**D05k — Full signed fixed-width range:** a signed N-bit integer represents −2^(N−1) through 2^(N−1)−1, inclusive. A signed 7-bit integer therefore holds −64 through 63, and a signed 1-bit integer holds −1 or 0. Each bit pattern represents a distinct mathematical value. Negating the minimum produces an out-of-range result and reports overflow under D05e. This selects mathematical ranges, not memory layout. D05n settles unsigned ranges. Exact encoding, remaining arithmetic rules beyond D05s–w and D05y–aj, and remaining conversion rules remain open; D05l settles fixed-width type notation.

**D05l — Fixed-width integer notation:** write a signed fixed-width integer type as `int[length=x]` and an unsigned one as `uint[length=x]`. Here `x` supplies the bit length, known at compile time under D05h, allowed to use constants and arithmetic under D05j, and positive under D05i. For example, `int[length=7]` and `uint[length=19]` are accepted type forms. D05m names the ordinary automatically growing integer `int`. This notation does not imply a bare unsigned-growing type or settle generic/named-argument syntax elsewhere. Detailed expression grammar, remaining conversion rules and memory encoding remain open; D05n settles unsigned ranges.

**D05m — Ordinary integer name:** bare `int` denotes the ordinary signed, arbitrary-precision integer that grows as needed under D05c. `int[length=x]` continues to denote a signed fixed-width type under D05l. This chooses the type name only; annotation/declaration grammar, remaining conversion rules, representation, and any bare unsigned-growing type remain open.

**D05n — Full unsigned fixed-width range:** `uint[length=N]` represents 0 through 2^N − 1, inclusive. Thus `uint[length=7]` holds 0 through 127, and `uint[length=1]` holds 0 or 1. Arithmetic producing a result outside the range reports overflow under D05e, including subtraction below zero. This chooses mathematical ranges only; exact encoding, remaining conversion rules, remaining arithmetic rules beyond D05s–w and D05y–aj, and the error mechanism remain open.

**D05o — Automatic lossless integer conversions:** when assigning an already-typed integer, passing it as a function argument, or returning it, automatically convert if the destination type can represent every value of the source type. This depends on the full source type range, not just the current value. Examples: `int[length=7]` to `int[length=16]`, `uint[length=7]` to `int[length=8]`, and any fixed-width integer to ordinary growing `int`. Other conversions between distinct integer types require an explicit request, even when the current value fits. D05p settles out-of-range explicit conversion behavior. D05q settles integer conversion syntax. D05r settles direct integer literal typing. D05s–w settle integer addition/subtraction/multiplication typing, D05y–aj settle several integer division rules, and D05at settles exact rational addition. Remaining division operand/context rules, integer quotient/modulo, mixed rational operands, other operators, and resource-exhaustion behavior remain open.

**D05p — Checked explicit integer conversions:** an ordinary explicit integer conversion reports an error when the runtime value is outside the destination type’s representable range, rather than wrapping or clamping. For example, converting ordinary `int` values 300 or −1 to `uint[length=8]` fails because that type holds 0 through 255. This applies to signed and unsigned destinations. D05q settles integer conversion syntax. The error representation and handling mechanism and any separate explicitly requested wrapping/clamping facilities remain open; D05x settles constant-failure timing.

**D05q — Call the destination integer type to convert:** explicitly convert an integer value by writing the destination type followed by the parenthesized value. Accepted forms include `int[length=8](value)`, `uint[length=8](value)`, and `int(value)` for the growing signed integer. D05p’s range checks apply to bounded destinations. This establishes integer-to-integer conversion syntax only; it does not settle class construction, general function-call grammar, type values, parsing strings, or conversions from other kinds of value.

**D05r — Contextual integer literals:** a direct integer literal takes the expected integer type when its mathematical value fits that type’s range. Without an expected integer type, it has ordinary growing type `int`. For example, passing literal `42` directly to a parameter typed `uint[length=8]` needs no explicit conversion; literal `300` in that position is a compilation error because it does not fit. This is literal typing, not an exception to D05o’s full-source-range rule for already-typed values. D05v–w settle expected-type propagation for direct-literal and literal-only addition/subtraction/multiplication trees, including bounded intermediate checks. Constant expressions and contextual typing outside that scope, conversion-operand context, overload resolution, remaining arithmetic rules beyond accepted integer division and rational addition, and detailed literal/sign grammar remain open. D05x settles constant arithmetic overflow and out-of-range conversion failures.

**D05s — Common operand type for integer addition, subtraction, and multiplication:** for two already-typed integer operands, use an existing operand type whose representable range contains both operand types’ full ranges. Automatically convert the other operand to that type; the result has that same type. Identical operand types retain their type. Thus signed 7-bit with signed 16-bit uses `int[length=16]`, and any fixed-width integer with growing `int` uses `int`. If neither operand type contains the other’s range, reject the operation during compilation unless an explicit conversion makes the types compatible; signed 8-bit with unsigned 8-bit is such a case. Do not synthesize a new common type. Fixed-width results retain D05e’s overflow checks rather than gaining extra result bits. D05t settles a direct literal paired with a typed operand. D05u settles destination context for a single operation with a typed operand. D05v settles single operations between two direct literals. D05w settles nested addition/subtraction/multiplication typing. D05y chooses fractional `/` for integer operands. Remaining division/modulo rules, comparisons, and other operators remain open.

**D05t — A direct arithmetic literal uses the typed operand’s type:** addition, subtraction, or multiplication of one already-typed integer and one direct integer literal gives the literal the typed operand’s type when it fits. This applies in either operand order; the result retains that type. An out-of-range literal is a compilation error. For a `uint[length=8]` operand, literal `1` fits; adding it to a current value of 255 overflows under D05e, while literal `300` is rejected during compilation. This avoids silently promoting fixed-width arithmetic to growing `int` merely because it contains a literal. D05u makes this independent of an outside expected result type for a single operation. D05v settles single operations between two direct literals. D05w settles nested addition/subtraction/multiplication typing. Other constant expressions and detailed literal/sign grammar remain open.

**D05u — Compute from operands before converting the result:** for a single addition, subtraction, or multiplication containing at least one already-typed integer operand, determine the operand and computation type under D05s–t, compute with that type’s arithmetic, then apply result conversion under D05o if the surrounding assignment, argument, or return needs a different type. A wider expected result type does not widen the computation or resolve incompatible operand types. For example, adding `uint[length=8]` values currently holding 200 and 100 overflows even when the destination is `uint[length=16]`. Explicitly converting an operand to `uint[length=16]` first makes that example compute in unsigned 16-bit and produce 300. This also preserves D05t’s typed-operand rule for direct literals despite an outside expected type. D05v settles single operations between two direct literals. D05w settles nested addition/subtraction/multiplication typing.

**D05v — Expected type for arithmetic between two direct literals:** for one addition, subtraction, or multiplication directly between two integer literals, use the expected integer type for both operands and the result. Each literal must fit that type’s range or compilation fails. The operation still follows the type’s arithmetic and overflow behavior: adding literals 200 and 100 with expected type `uint[length=8]` overflows even though each operand fits. Without an expected integer type, both operands and the result use growing `int`. For example, adding literals 1 and 2 for an unsigned 8-bit destination needs no explicit conversion. D05w settles nested addition/subtraction/multiplication typing. D05x settles constant-failure timing. D05y–aj settle several integer division rules, and D05at settles exact rational addition. Contextual typing for other operators and the remaining operator rules stay open.

**D05w — Recursive contextual typing for literal-only arithmetic:** extend D05s–v recursively through addition, subtraction, and multiplication. A subtree made entirely of integer literals and these operations can receive a contextual integer type. If its sibling has a known integer type, use that type throughout the literal-only subtree; for example, adding a `uint[length=8]` value to the product of literals 2 and 3 computes both product and sum in unsigned 8-bit. If the whole expression contains only literals, use its expected integer type throughout, or growing `int` if none exists. Each literal must fit its supplied type, and each intermediate operation retains that type’s overflow checks: with expected unsigned 8-bit, adding 200 and 100 before subtracting 100 still overflows. Subtrees containing already-typed values determine their own types from operands, independent of an outside expected result type; a wider outer operation does not retroactively widen them. This does not make arbitrary compile-time expressions literal-like. D05y–aj settle several integer division rules, and D05at settles exact rational addition. Contextual typing for other operators, named-constant contextual rules, conversion-operand context, detailed literal/sign grammar, and failure behavior outside the accepted constant-error rules remain open.

**D05x — Constant integer range failures are compilation errors:** reject fixed-width integer overflow and out-of-range integer conversions during compilation when the calculation is evaluable from integer literals, named compile-time integer constants, and built-in integer arithmetic/conversions. Apply this wherever such an expression is written in ordinary code, including branches that would never execute. Examples include `uint[length=8](300)` and adding literals 200 and 100 with expected type `uint[length=8]`. This is constant calculation validation, not a requirement to prove arbitrary facts about runtime inputs. Contexts requiring compile-time values, including bit-width expressions, still require valid results. Runtime-dependent failures retain their error behavior; error representation/handling, additional analysis of runtime-derived facts, exact constant-expression evaluation rules and resource limits remain open.

**D05y — Fractional division between integers:** `/` with integer operands means fractional division rather than an integer quotient. For example, `5 / 2` has value 2.5. The result uses a numeric type capable of fractions even when the mathematical quotient is a whole number; D05z selects binary64 floating-point as that result type. An integer-quotient operation, its spelling and negative rounding, operand compatibility, contextual typing, conversions and large-integer division details remain open. D05z explicitly selects floating-point representation; D05ab settles zero-divisor errors.

**D05z — Binary64 result for integer division:** `/` between integer operands produces a 64-bit binary floating-point (binary64) result, including when the quotient is whole. `5 / 2` is exactly 2.5; `1 / 3` is approximated because binary64 cannot represent one third exactly. Davis chose this over exact rational and decimal arithmetic for everyday speed and bounded result storage. D05ae selects nearest, ties-to-even rounding for ordinary finite results. D05ah extends nearest/ties-even through subnormals and eventual zero without underflow errors. D05aj names the type `float`. Other special-value rules, operand compatibility/contextual typing, and conversions remain open; D05af selects an overflow error, with the precise upper rounding boundary still open. D05ad selects rounding the mathematical quotient once, without first rounding operands. Defaults for other fractional expressions remain open.

**D05aa — Standard-library exact rational type:** the standard library must provide an exact rational-number type. This supplements D05z: integer `/` still produces binary64. D05ak names the type `rational`. D05al permits growing numerator/denominator sizes. D05aq settles two-integer construction spelling/order. Imports, remaining construction details, storage layout and resource policy, remaining arithmetic/operator behavior (exact rational + in D05at), remaining normalization details, comparisons, conversions, and error handling remain open.

**D05ab — Integer fractional division by zero reports an error:** when both operands of `/` are integers and the divisor is zero, report an error instead of producing infinity or NaN. Both `5 / 0` and `0 / 0` fail. This catches invalid calculations at the operation, at the cost of a failure path. D05ac settles constant-case compilation timing; error representation/handling remain open. This does not settle zero division for floating-point operands or the rational library type.

**D05ac — Constant integer division by zero fails compilation:** reject integer `/` with a zero divisor during compilation when the calculation is evaluable from integer literals, named compile-time integer constants, and built-in integer arithmetic/conversions. Apply this wherever written in ordinary code, including unreachable branches. For example, `5 / 0` and `0 / 0` fail compilation even if never executed. This extends the early constant-validation direction of D05x without requiring proof of arbitrary facts about runtime inputs. Runtime-dependent zero divisors retain D05ab’s error behavior. Required compile-time contexts still require valid values; exact constant-expression rules, resource limits, further runtime-derived analysis, and error representation/handling remain open.

**D05ad — Round the integer quotient once:** define integer `/` with a nonzero divisor by the mathematical quotient of the exact integer operands, rounded once to binary64. Do not first approximate each operand as binary64. A huge nonzero integer divided by itself yields binary64 value 1 even when the operand exceeds binary64’s finite range, subject to available computation resources. This avoids information loss before division at the cost of division support beyond independently converting operands and using hardware floating-point division. It does not require constructing a rational object or prescribe an algorithm. D05ae settles ordinary finite-result rounding and D05ah settles tiny results; the precise upper rounding boundary, resource-exhaustion behavior, operand compatibility/contextual typing, and conversions remain open.

**D05ae — Nearest, ties-to-even rounding for integer division:** for ordinary finite binary64 results of integer `/`, choose the representable value nearest the exact mathematical quotient. If exactly halfway between adjacent representable values, choose the one whose least significant stored significand bit is zero (even). This rounds only the quotient under D05ad. Chosen over nearest with ties away from zero and rounding toward zero, retaining nearest-value accuracy without consistently increasing magnitude on ties. D05af selects overflow errors and D05ah extends this rounding through subnormals and zero. D05ai settles zero-result signs. The precise upper rounding boundary and applying this rule to other operations remain open.

**D05af — Integer division result overflow reports an error:** if integer `/` overflows its binary64 result, report an overflow error instead of producing signed infinity. For example, an integer equal to 10 to the power 400 divided by 1 overflows. This checks the quotient, not the operand sizes: huge equal nonzero operands still yield 1 under D05ad, subject to resources. Chosen over infinity to catch out-of-range calculations, at the cost of a failure path. D05ag settles constant-case reporting timing. The precise upper rounding/overflow boundary, error representation/handling, and other operations remain open; D05ah settles tiny-result behavior and D05ai settles zero-result signs.

**D05ag — Constant integer division result overflow fails compilation:** reject binary64-result overflow from integer `/` during compilation when evaluable from integer literals, named compile-time integer constants, and built-in integer arithmetic/conversions. Apply this wherever written in ordinary code, including unreachable branches. This follows D05x and D05ac, catching constant mistakes early at the cost of requiring valid constant calculations in dead code. It does not require proving arbitrary facts about runtime inputs. Runtime-dependent result overflow retains D05af’s error behavior, and required compile-time contexts still need valid values. The precise overflow boundary, exact constant-expression rules/resource limits, additional runtime-derived analysis, and error representation/handling remain open.

**D05ah — Subnormal integer division results and eventual zero:** extend nearest, ties-to-even rounding of the exact integer `/` quotient through binary64 subnormal values down to zero. Preserve a subnormal result when selected by that rounding rule; a sufficiently tiny nonzero mathematical quotient may round to zero. Do not report an underflow error for these tiny results, including in constant calculations. Chosen over rejecting every nonzero quotient below the smallest normal binary64 magnitude. This retains tiny values where possible and permits computation to continue, at the cost of decreasing relative precision and eventual loss of a nonzero result. D05ai settles zero-result signs. Behavior of other operations, resource exhaustion, and general constant-evaluation details remain open.

**D05ai — Preserve the division sign for zero results:** when integer `/` produces a binary64 zero, preserve the division sign rather than always using positive zero. A tiny negative mathematical quotient rounded to zero produces negative zero. For an exactly zero numerator, treat integer zero as positive when determining the division sign: `0 / -5` produces negative zero and `0 / 5` produces positive zero. Division by a zero denominator still errors under D05ab. This retains sign information at the cost of two zero representations. Printing, comparisons, other floating-point operations, and sign-inspection facilities remain open.

**D05aj — Binary64 type name `float`:** the exact lowercase name `float` denotes the fixed-precision binary64 type produced by integer `/`. Chosen over `float64` for a short everyday type name, at the cost of not showing the format’s width in the spelling. Unlike growing `int`, `float` has fixed precision and range. This names the already-selected type only; other floating types, floating literal defaults/grammar, and conversions or constructor-like calls remain open; D05ak names the rational type.

**D05ak — Standard-library exact type name `rational`:** the exact lowercase name `rational` denotes the required standard-library exact rational-number type. Chosen over `fraction` for an explicit mathematical name. This settles the type’s own name only, not a module/import path or automatic availability. D05al settles growing numeric range. D05aq settles two-integer construction spelling/order. Remaining construction details, storage layout and resource policy, remaining arithmetic/operators (exact rational + in D05at), remaining normalization details, comparisons, conversions, and errors remain open. **D05al — Automatically growing rational numerator and denominator:** `rational` supports exact ratios of integers without a fixed bit-width ceiling on numerator or denominator, growing automatically subject to available resources, like `int`. Chosen over fixed-size limits to permit very large exact fractions, at the cost of increasing memory and arithmetic work as values grow. This selects numeric range rather than physical storage layout. D05am selects automatic reduction to lowest terms. Remaining normalization details, intermediate arithmetic, resource-exhaustion behavior, remaining construction details (spelling/order in D05aq), and optional alternative rational types remain open.

**D05am — Automatically reduce rational fractions:** `rational` automatically reduces fractions to lowest terms by cancelling common factors of numerator and denominator, without a manual simplification request. For example, the mathematical fraction six eighths reduces to three quarters. This applies to rational values produced by construction or supported arithmetic without selecting those APIs/operators. It keeps fractions simplified at the cost of reduction work. D05an selects positive denominators and canonical zero. D05ao selects an error for zero-denominator construction. Physical storage and internal reduction strategy/timing and remaining arithmetic API beyond exact rational + in D05at remain open.

**D05an — Positive rational denominators and canonical zero:** valid reduced `rational` values always have a positive denominator; any negative sign belongs in the numerator. Six over negative eight reduces to negative three over positive four; negative six over negative eight reduces to positive three over positive four. Together with D05am’s lowest-term reduction, zero has mathematical fraction form 0 over 1. Chosen over allowing either denominator sign to give one reduced mathematical fraction form per value. This does not prescribe physical storage or printed syntax. D05ao selects an error for zero-denominator construction. D05aq settles two-integer construction spelling/order; remaining construction details and APIs remain open.

**D05ao — Zero-denominator rational construction reports an error:** creating a `rational` with denominator zero reports an error, for both a nonzero numerator and a zero numerator. D05aq settles two-integer construction spelling/order. Remaining construction details, error representation/handling, and remaining rational arithmetic operators beyond exact + in D05at remain open.

**D05ap — Constant zero-denominator rational construction fails compilation:** reject creation of a `rational` whose denominator evaluates to zero during compilation, wherever written, including unreachable ordinary code. D05aq settles two-integer construction spelling/order. Remaining construction details, error representation/handling, detailed constant-evaluation rules/resource limits, and remaining rational arithmetic operators beyond exact + in D05at remain open.

**D05aq — Construct a rational by calling its type:** the two-integer construction spelling is `rational(numerator, denominator)`, with numerator first and denominator second; for example, `rational(3, 4)` creates three quarters. Chosen over `make_rational(3, 4)` for a short spelling consistent with the type-call shape of integer conversions, at the cost of type calls serving both construction and conversion. **D05ar — Integer-only two-argument rational construction:** both arguments to `rational(numerator, denominator)` must be integers. A `float` argument is a compile-time type error even when its current value is a whole number. Chosen over also accepting finite whole-valued floats to keep this construction exact and avoid implicit float-to-integer conversion, at the cost of a separate explicit facility if a programmer needs to convert a float. **D05as — Independent integer types in rational construction:** each already-typed argument to `rational(numerator, denominator)` may independently be growing `int`, signed fixed-width `int[length=N]`, or unsigned fixed-width `uint[length=N]`. Their types need not match; for example, a signed 8-bit numerator and an unsigned 16-bit denominator are permitted together. Preserve each exact integer value without narrowing or wrapping before construction. Chosen over requiring matching integer types for convenience and compatibility with growing rational range, at the cost of supporting multiple integer input types. This does not require a particular conversion implementation or settle literal contextual typing, general mixed arithmetic, or other conversion facilities. **D05at — Exact rational addition with `+`:** when both operands have type `rational`, `+` computes their exact mathematical sum and returns a `rational`, subject to available resources. One third plus one sixth produces one half; apply D05am–an automatic reduction, positive denominators, and canonical zero without float rounding. Chosen over a named library addition operation for familiar arithmetic syntax, at the cost of operator support for the standard-library type. Mixed integer/float operands, other operators, resource-exhaustion behavior, and implementation strategy remain open. D12j–l separately require custom-class `+`, select `@add` as a marker above an ordinary method, and choose the left instance receiver/right operand argument shape. Further signature/dispatch rules remain open.

**D05au — Integer `%` is the mathematical remainder:** for integer operands, `a % b` is the remainder with the sign of the divisor `b`, so `a == (a // b) * b + a % b` holds with the quotient rounded toward negative infinity, as in Python. For example `7 % 3` is 1, `-7 % 3` is 2, `7 % -3` is -2 and `-7 % -3` is -1. Davis wrote “like mathematical remainder like Python”. A zero divisor is an error; the prototype applies the operand-type rule of D05s to the result type for fixed-width integers. Float and rational operands, an integer-quotient operator, constant zero divisors at compile time, and error wording remain open.
