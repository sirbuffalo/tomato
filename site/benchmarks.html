Method

  • Same work. Each language implements the same loop-for-loop algorithm (no tricks such as caching that only one language could use) and prints a checksum. benchmarks/run.sh compares every version's output with the Tomato version's: the smoke run that the test suite makes fails on any difference, and a full run prints a warning and records "agrees": false in the JSON.
  • Builds. Every number below used the command shown here. Tomato is built by this repository's own compiler twice: in release mode (no leak checks, short error codes) and in debug mode (leak checks and full error text), and each is shown separately. Go, Rust, C, C++, C# and Swift use their usual optimized builds, Java runs on the HotSpot virtual machine, JavaScript and TypeScript on Node (TypeScript with its types stripped, so it runs as the same JavaScript), and PHP and Python are the interpreters as installed. A language whose tools were not installed when the suite ran has no box.
    • Runs. Each program runs 10 times (Python and PHP too). The runs of every benchmark and language are shuffled into one random order with a fixed, recorded seed, rather than run back to back, so thermal throttling and background load fall evenly on every row. The table shows the median, the fastest run and the spread (slowest minus fastest, over the median); every time is in benchmarks.json. Time is the wall clock of the whole process (including start-up: a few milliseconds for the compiled programs, and tens of milliseconds for Java, C# and Node), and memory is the peak resident size.
    • Not tuned. The programs are written the way a beginner in each language would write them: lists, strings and dicts from the standard library, objects as separate heap allocations (a Box in Rust, a pointer in Go). Nobody hand-tuned any version.

    Caveats

    • One machine, one run of the suite, fixed inputs. More than half of the timings varied by more than 20% between the fastest and slowest run. Other programs ran on the machine at the same time (the load average is at the top of the page), so small differences are noise; the spread between the fastest and slowest run is in the JSON.
    • Tomato is young and its compiler does little optimization of its own (release mode relies on clang and link-time inlining of the runtime). The numbers are a snapshot of this version, not a verdict on the language.
    • Tomato's int is unlimited in size, with small values held in one tagged word; Go, Rust and (for big values) Python pay different costs for numbers, so the integer benchmarks compare designs as much as compilers. The Go int and Rust u64 versions can overflow silently or stop; the checksums are chosen not to.
    • The sort benchmark compares different algorithms: Tomato's sorted is a radix sort for long lists of ints and floats and an introsort for the rest (up to v0.51 an introsort for all of them), C uses the library's qsort, C++ std::sort, Rust uses the standard library's sort (a stable merge sort), and Go its sort package. A Rust radix sort (benchmarks/sort/sort_radix.rs) is measured too and shown under the sort chart.
    • Every language uses its usual fast library for big integers: math/big in Go, the built-in int in Python, and the num-bigint crate in Rust (whose standard library has none), built with cargo build --release; benchmarks/bigint/Cargo.lock pins the crate versions. Java uses BigInteger, C# System.Numerics, and JavaScript and TypeScript BigInt. C, C++, Swift and PHP have none in their standard libraries, so those versions multiply an array of words by hand, which is not a general big-integer library. C has no hash table either, so its wordcount carries a small one. Tomato uses its own built-in int.
    • The mandelbrot checks use explicit float conversions in Go so that no fused multiply-add changes a result.
    • Rust and Go may inline or remove work a language without a heavy optimizer cannot; the checksums prevent removing it entirely, but loops can still be unrolled and vectorized.

    What the numbers suggest for Tomato

    The list is in docs/performance.md.

    1. Cut the checks that every integer operation still makes (a tag test and an overflow test) in numeric loops: matmul is 2.4 times slower than Go, and collatz, fib and sieve are 1.1 to 1.2 times slower (wall-clock medians in the table above).
    2. Allocate less in text code: split still makes one string per piece, and strings and wordcount spend most of their time in malloc and free.

    Since v0.48 release mode links the program and the runtime with link-time optimisation and the cycle collector skips objects that cannot form cycles; since v0.49 the compiler no longer counts references for reads of a variable that keeps its value alive, sorted is a native introsort and big integers are freed; since v0.50 small objects come from a size-class allocator, string paths work in place, range(a, b, step) loops are counted loops and sorted takes key= and cmp= functions.

    Source

    Everything is in the benchmarks/ folder: one folder per benchmark with its programs, sizes.txt (the inputs), run.sh (the runner), measure.c (the timing helper) and results/ (the numbers on this page). Run benchmarks/run.sh yourself; it needs clang and skips every other language whose tools are missing. The other languages' programs exist only as a comparison; Tomato's own tooling uses no Python.
